## 1. 项目定位与边界

### 1.1 一句话

**一个 CLI 无关的 git 提交闸门层**：未经审核的代码无法进入权威 git 历史。闸门在 git 接收端强制生效，锚定不可变 tree，审核员与执行模型跨模型独立，成本可度量。

### 1.2 三条自建理由（按强度排序）

1. **CLI 无关性是结构性的，不是配置出来的。**
   agent-mesh 的防线是 `--disallowedTools Bash`——per-CLI，每加一个 CLI 就要知道它的参数语法、是否有等价开关、会不会某天改掉。本项目的闸门在 git 接收端，**不关心 commit 是哪个 CLI 产生的**。在"多 CLI 是硬要求"这个前提下，这是唯一不退化的做法。
2. **接收端闸门 + tree 锚定，杜绝 TOCTOU。**
   审核对象是不可变的 `tree_hash`，push 时由服务端 hook 现场重算并比对。客户端任何 flag 都改不了这个等式（§3.4 已实测）。
3. **审核员跨模型独立 + 成本可度量。**
   审核引擎与执行 CLI 解耦（不同进程、不同模型、可配不同 provider）；每工单分别记录执行与审核成本，并设有止损判据（§7）。

### 1.3 相对 v2 草案的定位收窄

| v2 的内容 | 本文档的处置 | 理由 |
|---|---|---|
| Java + Spring Boot + JGit 后端 | **保留**，但范围只到闸门层 | 不涉及 PTY/前端，JGit 处理 tree/commit-tree/push 正是强项 |
| Vue 3 + Vite 前端 | **删除** | 闸门层不需要 Web UI；审核结果走 CLI/文件/MCP |
| 内嵌 PTY 终端（xterm.js、pty4j） | **删除** | 编排不是本项目职责；原 S2 spike 一并删除 |
| 项目/工单/看板/多终端 UI | **删除** | agtx / octomux / agent-mesh 已覆盖，非差异点 |
| 自研审核引擎（§7.2 分块、§7.3 schema） | **改为调用现成二进制** | `prism` / `local-review` 单二进制 + 确定性退出码 + JSON/SARIF |
| 随机一次性令牌 + 用后即焚 | **改为令牌绑定 `tree_hash`** | 实测证明 tree 绑定天然防重放，少一张表（§3.4） |
| S4 闸门路线三选一 | **收窄**：`pre-receive` + push-option 已实测可行 | 剩余问题只是"JGit 能否发 push-option" |

### 1.4 明确不做（本阶段）

- 工单看板、项目管理 UI、Web 前端
- 交互式终端 / PTY / 进程编排
- agent 调度与上下文注入（由上游编排工具负责）
- 自研审核 prompt 与分块策略（先用现成引擎的）
- 多用户、认证体系之外的权限模型、远端协作

## 2. 三层架构与职责边界

```
┌─────────────────────────────────────────────────────────────┐
│ 编排层（不自建，可选接入）                                    │
│ agtx / octomux / agent-mesh / 人手工                          │
│ 职责：起 agent、给任务、管 worktree 生命周期                   │
└───────────────────────────┬─────────────────────────────────┘
                            │ 触发预提审（MCP 或 CLI）
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ 闸门层（本项目，从零写，Java）                                │
│ ① presubmit：固化工作区为 tree 对象，产出 tree_hash            │
│ ② review：调审核引擎，拿结构化 findings，判 pass/reject        │
│ ③ commit+push：commit-tree 提交被审的 tree，携 tree 令牌 push  │
│ ④ 权威 bare 库的 pre-receive 现场重算 tree 并比对              │
│ ⑤ 成本埋点：执行/审核 token 分别记账                          │
└───────────────────────────┬─────────────────────────────────┘
                            │ ProcessBuilder 调用
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ 审核引擎层（不自建，调现成二进制）                            │
│ dshills/prism 或 mshykov/local-review                        │
│ 输入：diff + 上下文 ｜ 输出：JSON/SARIF + 确定性退出码          │
└─────────────────────────────────────────────────────────────┘
```

### 2.1 边界铁律

- **闸门层不 spawn agent CLI**。谁起 agent 是编排层的事。闸门层只接受"某个 worktree 想提交"这个请求。
- **闸门层不自己做 LLM 调用**。审核一律经审核引擎二进制，闸门层只负责组装输入、解析输出、执行判定。
- **权威库只有闸门层能 push**。agent 的 worktree 里可以随便 commit，无所谓。

## 3. 关键技术契约（已实测部分标注）

### 3.1 仓库拓扑

```
<project>/
├── auth.git/                    ← 权威 bare 库，agent 永不访问
│   └── hooks/pre-receive        ← 闸门（服务端侧，客户端 flag 跳不过）
└── worktrees/
    ├── TICKET-1/                ← agent 活动区，可任意 commit
    └── TICKET-2/
```

### 3.2 预提审：固化 tree

```
1. 在 worktree 内：git add -A            （含 untracked）
2. git write-tree                        → tree_hash（不可变）
3. 记录：ticket_no, review_round, tree_hash, base_commit, target_branch
4. git diff <base_commit> <tree_hash>    → diff 文本（落盘，DB 存路径+哈希）
```

`tree_hash` 是后续所有环节的唯一锚点。

### 3.3 审核：调外部引擎

```
ProcessBuilder: prism review <mode> --format json [--provider ollama]
→ stdout JSON  +  exit code
→ 解析为统一 findings 结构（severity/file/line/message）
→ 判定：任一 blocker → reject；仅 warning/nit → 按严格度配置
→ fail-closed：超时 / 崩溃 / JSON 不可解析 → 一律 reject
```

**统一 findings 结构由闸门层定义**，不同引擎写各自的 adapter。这样换引擎不影响判定逻辑。

### 3.4 放行：commit-tree + push-option 令牌（已在 Windows 实测）

**环境**：Windows 11 + git 2.37.1.windows.1。权威库需 `git config receive.advertisePushOptions true`。

```
闸门层（审核通过后）：
  1. 复算 worktree 当前 tree，与 tree_hash 比对；不一致 → 拒绝，退回预提审
  2. git commit-tree <tree_hash> -p <base_commit> -m <msg>   → commit_sha
  3. git push --push-option=tree=<tree_hash> auth.git <commit_sha>:refs/heads/<branch>

pre-receive（服务端）：
  read old new ref
  tree=$(git cat-file -p $new | sed -n 's/^tree //p')     ← 现场重算，不信客户端
  [ "$GIT_PUSH_OPTION_0" = "tree=$tree" ] && exit 0 || exit 1
```

> 上面是**实测用的最小脚本**，只校验 tree。生产脚本必须补全 §5.2 列出的 4 条判定（ref 白名单、fast-forward、option 数量），否则 B7/B8 可绕。

**实测矩阵**（临时 repo，已清理）：

| # | 场景 | 结果 |
|---|---|---|
| 1 | push-option 能否到达 hook | 通，`GIT_PUSH_OPTION_0` 收到 |
| 2 | `--no-verify` 且无令牌 | **REJECT** |
| 3 | 令牌与实际 tree 一致 | ACCEPT |
| 4 | 拿旧令牌推新 commit（重放） | **REJECT**（tree 不匹配） |
| 5 | `-c core.hooksPath=/dev/null --no-verify` | **REJECT** |
| 6 | 全程权威库 HEAD | 未被污染 |

**由此得到的简化**：令牌不需要是独立随机串、不需要"用后即焚"表。**令牌 = `tree=<tree_hash>`，天然防重放**——hook 现场从 commit 对象反查 tree，客户端无法伪造这个等式。相比 v2 §6.4 的设计少一张表、少一套过期逻辑。

**残留风险（必须承认）**：agent 与闸门层同 OS 用户同权限，agent 可以直接对 `auth.git` 做文件级写入，或改掉 hook 本身。闸门防的是"走 git 协议的未审提交"，不是"有 shell 的对手"。绝对隔离需 OS 级手段（独立用户 + ACL / 容器），不在本阶段范围。

### 3.5 崩溃恢复

- **git 是最终真相**。启动时 reconcile：`tree_hash` 对应 commit 已在目标分支 → 工单置完成；否则退回待提交。
- **push 幂等**：以 `(ticket_no, review_round, tree_hash)` 为幂等键，重复执行不产生第二个 commit。
- **上游状态不明**：push 已发出但无法确认是否被接受 → 标记 ambiguous，记日志，要求人工裁决，**不自动重试**。

### 3.6 并发

- 一工单一 worktree。
- 同项目 git 写操作串行（进程内锁 + `.lock` 文件 + 陈旧锁超时清理）。JGit 不保证跨进程安全。
- 并发工单上限 4（可配）。

总原则：**P0 是硬闸，三个 spike 不全过不许进 P1。** 每个阶段都有可运行的验收命令，跑不过就不算完成。

### P0 — 前置验证（硬闸，不写业务代码）

目标：确认"哪些不用自己写"，以及"闸门能不能落在 JGit 上"。

| # | Spike | 具体做什么 | 通过判据 | 失败后果 |
|---|---|---|---|---|
| **S1** | agent CLI 能否注入自定义 MCP 配置 | 对 opencode / claude code 各试：能否在启动时指向本地 MCP endpoint、能否携带 token、能否限制可见 tool 集。参考 agtx 的 `claude mcp add-json --scope local` | 至少 2 个 CLI 能连上并成功调用一个自定义 tool | 降级为"文件协议"：agent 写约定文件，闸门层轮询触发预提审。**闸门本身不受影响** |
| **S3** | 审核引擎能否复用 | 在 Windows 跑通 `dshills/prism` 与 `mshykov/local-review`：指定 Ollama、喂一个真实 diff、检查 JSON 稳定性与退出码确定性、试一个 3000 行大 diff 看分块行为 | 至少 1 个引擎在 Windows 稳定产出可解析 JSON + 确定性退出码 | 才考虑自研审核层（工作量显著上升，需重新评估范围） |

**P0 交付物**：一份 `spike-结论.md`，每个 spike 写清"结论 + 证据命令 + 采纳的方案"。

### P1 — 闸门骨架（核心，最高优先级）

目标：**把 §3.4 的链路用代码跑通，并让 §5 绕过测试集全绿。**

任务：

1. 仓库拓扑初始化：创建 bare 权威库、装 `pre-receive`、置 `receive.advertisePushOptions=true`、创建 worktree。
2. `presubmit`：`add -A` → `write-tree` → 落 `tree_hash` / `base_commit` / diff（diff 落盘，DB 存路径+哈希）。
3. `commit_and_push`：复算 tree 比对 → `commit-tree` → 携 `--push-option=tree=<hash>` push。
4. `pre-receive` 脚本：现场 `cat-file` 反查 tree 并比对（脚本由系统生成，不手工维护）。
5. SQLite + Flyway/Liquibase 迁移骨架（表：ticket、presubmit、audit）。
6. 项目级串行锁。
7. **§5 绕过测试集与代码同步写，不后补。**

**交付物**：可用 CLI 完成 `presubmit → (人工判定 pass) → commit_and_push` 全链路。

**验收判据**：

| # | 判据 |
|---|---|
| A1 | 一个工单能走完全链路，权威库**该工单只新增一个 commit**（`rev-list --count <target>` == 操作前值 + 1，无重复 commit；base commit 属 `gate init` 引导播种，不算工单产物） |
| A2 | §5 的 B1–B8 全部 REJECT，权威库 HEAD 不变 |
| A3 | TOCTOU：审核后篡改 worktree，`commit_and_push` 拒绝并退回预提审 |
| A4 | 幂等：同 `(ticket, round, tree_hash)` 重复执行只产生一个 commit |
| A5 | 崩溃恢复：在 `commit-tree` 后与 push 中途各 kill 一次，重启 reconcile 后状态收敛、无重复 commit |

### P2 — 审核接入

目标：把 P0/S3 选定的引擎接进来，实现自动判定与 fail-closed。

任务：

1. 引擎 adapter（按 S3 结论，1 个引擎起步）+ 统一 findings 结构。
2. 判定规则：任一 blocker → reject；warning/nit 按严格度配置。
3. **fail-closed**：超时 / 崩溃 / JSON 不可解析 → 一律 reject。
4. 审核结果结构化落库 + 可导出（供上游 agent 修复）。
5. 驳回回喂：产出 agent 可直接消费的结构化结果（`review_round` 自增，退回进行中）。
6. 审核引擎版本与参数记入审核记录（保证历史可比）。

**验收判据**：

| # | 判据 |
|---|---|
| A6 | 有 blocker 的 diff 被自动 reject，权威库 HEAD 不变 |
| A7 | fail-closed：注入超时 / 崩溃 / 坏 JSON 三种情况，均 reject |
| A8 | 驳回结果可导出为结构化文件，含 file/line/severity/message |

### P3 — 接入方式（MCP 或文件协议）

目标：让上游编排工具（或 agent 自己）能触发闸门，形态由 S1 结论决定。

- **S1 通过** → 提供 MCP endpoint（Streamable HTTP/SSE，bind 127.0.0.1 + token）。tool 分两域：
  - agent 域：`presubmit_create`、`presubmit_get_diff`、`review_result_get`
  - 人/编排域：`review_run`、`commit_and_push`、`config_*`
  - **`review_run` 绝不下放给 agent**，否则可反复刷审核直到蒙过。
- **S1 失败** → 文件协议：agent 写 `.gate/request.json`，闸门层轮询处理，结果写 `.gate/result.json`。

**安全硬要求**（若走 MCP/HTTP）：bind 127.0.0.1、token 鉴权、校验 `Origin`/`Host`、两套独立凭据。

**验收判据**：

| # | 判据 |
|---|---|
| A9 | agent 域凭据调用任一人域 tool 返回 403 |
| A10 | 无 token / 错误 Origin 的请求被拒 |
| A11 | 至少 1 个真实 agent CLI 能完成"触发预提审 → 读驳回意见 → 修复 → 二轮通过" |

### P4 — 成本埋点与结论

目标：让立项假设 H1 可被数据否决。

任务：

1. 埋点：`exec_token_cost` / `review_token_cost`（prompt/completion 分开）、`review_round`、`diff_size`、引擎与模型标识。
2. 导出：CSV / JSON，够算中位数与一次通过率。
3. 收集 ≥ 20 个真实工单样本后判定。

**判定规则**：

- 审核成本占比 = `review / (exec + review)`，取中位数
- 一次通过率 = `review_round == 1 且 pass` 的占比

| 结果 | 动作 |
|---|---|
| 占比 < 20% 且一次通过率 > 60% | H1 成立，可考虑扩展 |
| 占比 20%–40% | 部分成立，先做增量审核优化再复测 |
| 占比 > 40% 或一次通过率 < 40% | **H1 证伪**，按 §7 止损 |

> 执行成本可能拿不到精确 token（取决于 CLI 是否输出）。拿不到时降级为"轮次 + diff 体积"的粗口径，并在文档中标注口径差异。

## 5. 绕过测试集（P1 的核心产出，与代码同步写）

这是本项目的**产品测试**——闸门是唯一价值，闸门测试就是价值测试。

### 5.1 原则

- 每种绕过方式写成一个独立测试，**统一断言：权威库目标分支 HEAD 不变**。
- 用 JGit 构造临时 repo（bare + worktree），测试后清理。
- **不依赖开发者本机 git 配置**：显式设置 `user.name` / `user.email` / `core.autocrlf`（Windows 上尤其重要）。

### 5.2 测试矩阵

| # | 攻击 | 期望 | 状态 |
|---|---|---|---|
| B1 | worktree 内 `git commit --no-verify` 后 push（无令牌） | REJECT | **已手工验证**（§3.4 场景 2） |
| B2 | `git -c core.hooksPath=/dev/null commit` 后 push | REJECT | **已手工验证**（§3.4 场景 5） |
| B3 | 删除本地 hook 后 commit 并 push | REJECT | 待自动化 |
| B4 | 纯 plumbing（`hash-object`/`write-tree`/`commit-tree`/`update-ref`）后 push | REJECT | 待自动化 |
| B5 | 重放旧令牌推新 commit | REJECT | **已手工验证**（§3.4 场景 4） |
| B6 | 携带合法令牌但 push 的 tree ≠ 令牌中的 tree | REJECT | **已手工验证**（等价场景 4） |
| B7 | 直接 push 到非目标分支绕过（如 `refs/heads/tmp`） | 按策略：非白名单 ref 一律 REJECT | 待补 |
| B8 | force push 覆盖已审历史 | REJECT（hook 拒非 fast-forward，除非显式放行） | 待补 |

> B7/B8 是 §3.4 手工实测时没覆盖的两个面，P1 必须补。特别是 B7：若 hook 只校验 tree 不校验 ref，agent 可以推到任意分支，再由人误 merge。
>
> **由此得到 hook 的完整判定条件**（§3.4 的实测脚本只做了第 2 条，P1 必须补全）：
>
> 1. `ref` 在白名单内（否则 REJECT）
> 2. `GIT_PUSH_OPTION_0 == "tree=<现场重算的 tree>"`
> 3. 该 push 是 fast-forward（除非显式放行）
> 4. `GIT_PUSH_OPTION_COUNT == 1`（防止塞多个 option 混淆解析）

### 5.3 fail-closed 测试（P2）

| # | 注入 | 期望 |
|---|---|---|
| F1 | 审核引擎超时（stub 挂住） | reject |
| F2 | 审核引擎崩溃（非零退出且无输出） | reject |
| F3 | 返回不可解析 JSON | reject |
| F4 | 返回合法 JSON 但缺必需字段 | reject |
| F5 | 审核引擎二进制不存在 | **拒绝启动服务**（而非放行） |

### 5.4 其他必测

- **TOCTOU**：审核通过后改 worktree → `commit_and_push` 拒绝（A3）。
- **幂等**：重复 `commit_and_push` 只产生一个 commit（A4）。
- **故障注入**：`commit-tree` 后 / push 中途 kill，reconcile 收敛（A5）。
- **权限域**（P3）：agent 域凭据遍历全部人域 tool，逐一断言 403。**清单驱动，新增 tool 必须同步扩展该测试**，避免漏测。

## 7. 止损条件（写在开工前，避免沉没成本）

任一条触发，立即停下重新评估，不许"再写一点就好了"：

1. **S3 失败**（无可用现成审核引擎）→ 自研审核层会让工作量翻倍。停，重新评估是否值得。
2. **S4 失败且 notes 路线也不可行** → 闸门无法落地，项目核心价值不成立。停。
3. **P1 的 B1–B8 有任何一条无法 REJECT** → 闸门是漏的，等于没有。停，重新设计而非打补丁。
4. **H1 证伪**（§4 P4，审核成本占比 > 40% 或一次通过率 < 40%）→ 缩减为"手工触发的审核工具"，放弃自动闸门定位。
5. **发现某个现成项目已完整覆盖三条自建理由**（§1.2）→ 停，改为给它提 PR 或做插件。

> 第 5 条需要在 P0 结束时复查一次——竞品信息检索于 2026-08，会过期。

## 8. 工程约定

### 8.1 技术栈（收窄后）

- **语言**：Java 17+，Spring Boot（仅作为服务容器与 DI；若最终只做 CLI，可退化为纯 Java + picocli）
- **Git**：JGit 为主；`ProcessBuilder` 调真实 git 用于 JGit 覆盖不到的场景（push-option、hook 触发、plumbing 边缘行为）
- **存储**：SQLite + Flyway/Liquibase 迁移。大对象（diff 全文、审核原始输出、审计日志）落文件系统，DB 存路径 + 大小 + 哈希
- **审核引擎**：外部二进制，`ProcessBuilder` 调用
- **无**：前端框架、PTY、xterm.js、Vue（定位收窄后全部移出）

### 8.2 目录结构（建议）

```
gate/
├── src/main/java/…/
│   ├── repo/          仓库拓扑：bare 库、worktree、hook 安装
│   ├── presubmit/     write-tree、diff 采集、落库
│   ├── review/        引擎 adapter、统一 findings、判定与 fail-closed
│   ├── publish/       commit-tree、push-option、幂等与 reconcile
│   ├── lock/          项目级串行锁
│   ├── metrics/       成本埋点与导出
│   └── api/           CLI（P1/P2）→ MCP endpoint（P3，按 S1）
├── src/main/resources/
│   ├── db/migration/  Flyway
│   └── hooks/         pre-receive 模板（由系统生成安装，不手工维护）
└── src/test/java/…/
    ├── fixture/       JGit 临时 repo 构造器
    ├── bypass/        B1–B8（最高优先级）
    ├── failclosed/    F1–F5
    └── recovery/      TOCTOU、幂等、故障注入
```

### 8.3 硬性工程规则

- **绕过测试与闸门代码同一个 commit**，不允许"先实现后补测试"。
- `pre-receive` 脚本由系统生成并安装，**不手工维护**；脚本内容纳入版本管理与测试。
- 不吞异常。审核链路上任何异常 → reject 并记录原因。
- 审计日志 append-only，与 DB 分离存放，便于 DB 被篡改时交叉比对。
- 每次放行记录：工单号、`review_round`、`tree_hash`、审核引擎与模型、时间；写入 commit message trailer（`Ticket:` / `Tree:` / `Reviewed-By:`）。

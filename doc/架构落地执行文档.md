### 0.1 本文档写作前做的实测（Windows 11 + git 2.37.1.windows.1 + Corretto 17.0.3 + Maven 3.9.9）

下列结论均由临时 repo 实跑得出，**不是推断**，临时目录已清理。它们直接改写了 `执行文档.md §3.4` 的若干假设：

| 实测 | 结论 | 对文档的影响 |
|---|---|---|
| push-option 到达本地 bare 库 hook | 通，`GIT_PUSH_OPTION_0/COUNT` 可读 | §6 沿用 |

| `tree_hash` 随 `core.autocrlf` 变化（同字节不同 tree） | 固化/复算必须钉死 git 配置 | §3.3 采纳 |
| `commit-tree` 对 tree==base_tree 空 diff 照样成功 | 空轮次必须显式拦 | §3.3、§7 采纳 |
| 固定 author/committer/date 的 `commit-tree` | 同输入 → 同 SHA（确定性可复算） | §7 崩溃恢复依赖此 |
| 审核引擎 `prism`/`local-review` | **均 shell 调 live git，无法直接审不可变 tree**；但可对 dangling commit 用 commit 模式审 | §3.4、§5、S3 |

## 1. 项目定位与威胁模型（诚实声明）

### 1.1 一句话

**一个 CLI 无关的 git 提交闸门层**：未经审核的代码无法**经 git 协议**进入权威 git 历史。闸门在 git 接收端（bare 库 `pre-receive`）强制生效，锚定不可变 tree，审核员与执行模型跨模型独立，成本可度量。

### 1.2 修正 `执行文档.md §1.2` 的第 1 条自建理由

原文称「CLI 无关性是**结构性**的」。实测（B14）与残余风险（§1.3）表明这个措辞过强，应改为：

> **闸门是一个单一收口点，其强制生效不依赖任何 CLI 的 flag 或配置。** 这仍是相对 agent-mesh 的 `--disallowedTools Bash`（per-CLI、随上游版本悄悄失效）的真实优势——但它防的是「协议层的未审提交」，不是「持有 shell 的对手」。

### 1.3 威胁模型（必须写进文档，不得含糊）

**闸门防的是「无意的错误与走捷径」，外加「事后可检测」。它不隔离一个与自己同 OS 权限、持有 shell 的对手。**

同一 OS 用户下，持 shell 的 agent 可以：改写 `hooks/pre-receive`、设 `auth.git` 的 `core.hooksPath`、直接 `git -C auth.git update-ref`、`git push --receive-pack=<自带脚本>`、写伪造 approval、改 `gate.db`、改 `audit.jsonl`。**任何令牌设计与密码学都堵不住**，因为 hook 能读的密钥 agent 也能读——密码学无法在同权限的两个进程间造出权限边界。

但这不是放弃设计的理由，反而让定位更诚实、更站得住脚：**真实对手不是攻击者，是一个模仿 README/文档/shell 历史里现成 push 命令的 LLM。** 它不攻击闸门，它走它能看到的最短路。单一协议收口点能挡住它会找到的每一条捷径——**前提是那条捷径不是「文档里那条 push 命令把 tree 填上」**（这正是执行文档 §3.4 原方案的洞）。

文档正文必须包含这段声明（逐字，或等义）：

> 闸门阻止未审核代码**经 git 协议**进入权威历史。它不容纳一个同 OS 权限持 shell 的对手；此类对手可改写 hook 或直接写 ref。其保证是：(1) 每条进入 `auth.git` 的协议层路径都被检查；(2) 没有任何 CLI flag 或客户端配置能关掉该检查；(3) 蓄意绕过必须在 git 协议之外做文件级写入，且会留下可检测证据（hook 哈希漂移、ref reflog、哈希链审计日志）。它是对错误与捷径的防御，加上事后检测——不是隔离。

**唯一便宜的、通往真实边界的升级路径**（比容器更适合本场景，列为触发式，不现在做）：让 `pre-receive` 校验一个「对 `(ref,old,new,tree)` 的签名，签名密钥 agent 无法使用」——OS keystore 或需用户在场的硬件令牌。代价是每次放行一次在场确认。

### 1.4 明确不做（本阶段）

- 工单看板、项目管理 UI、Web 前端、交互式终端/PTY、agent 调度（编排层职责）
- 自研审核 prompt 与分块策略（先用/包装现成引擎）
- 多用户、认证体系之外的权限模型、远端协作
- 合并提交（merge commit）审核——tree 快照模型表达不了，presubmit 遇到 `MERGE_HEAD`/`CHERRY_PICK_HEAD` 一律拒（§7）

## 2. 仓库拓扑与边界铁律

### 2.1 拓扑（修正 `执行文档.md §3.1`）

```
<gate-home>/                         ← 闸门自有状态目录，agent 无理由访问
├── gate.db                          ← SQLite 主库（WAL）
├── blobs/<project>/<ticket>/<round>/  ← diff 全文、引擎原始输出、审计大对象
├── approvals/                       ← 一次性放行凭据（hook 读，路径烘焙进 hook）
│   └── consumed/                    ← 已消费凭据归档
├── audit.jsonl                      ← 哈希链审计日志（append-only，永不轮转）
└── hooks/pre-receive.tmpl           ← hook 模板（系统生成安装，纳入版本管理）

<project>/
├── auth.git/                        ← 权威 bare 库，agent 永不访问
│   └── hooks/pre-receive            ← 由模板生成安装；内容哈希登记在审计日志
└── clones/                          ← 注意：是 clone，不是 worktree（见 2.2）
    ├── TICKET-1/                     ← 独立 clone，agent 在其中可任意 commit
    └── TICKET-2/
```

### 2.2 铁律零（新增，实测 B14 强制）：agent 仓库必须是独立 clone，绝不用链接 worktree

`git worktree add` 产生的链接 worktree **与 `auth.git` 共享对象库与 ref store**。实测证明，在链接 worktree 内一条 `git update-ref refs/heads/main <sha>` 即可直接改写权威分支，**不触发 receive-pack、不触发 `pre-receive`、不走 push**——整个闸门被绕过。这不是 `执行文档.md §5.2 B4`（B4 是「plumbing 后 push」），这是「用 plumbing **代替** push」。

**约束**：
- agent 仓库一律 `git clone --no-hardlinks --single-branch --branch <target> <auth.git> clones/<ticket>`。
- `--no-hardlinks` 保证对象库物理独立；被拒绝的 push 其对象经 quarantine 丢弃，不会永久落进 `auth.git`。
- **启动 preflight（§10）拒绝**任何 `.git` 是文件（链接 worktree 标记）或 `objects/info/alternates` 指向 `auth.git` 的 agent 仓库。

### 2.3 边界铁律（保留 `执行文档.md §2.1` 并强化）

- **闸门层不 spawn agent CLI**。谁起 agent 是编排层的事。
- **闸门层不自己做 LLM 调用**。审核一律经外部引擎二进制。
- **权威库只有闸门层能经协议 push**；agent 的 clone 里随便 commit，无所谓——因为它推不进去（除非绕到协议之外，那属 §1.3 承认的残余风险）。

## 3. 核心流水线（重排，落实实测结论）

### 3.1 阶段总览

```
presubmit ── 固化不可变 tree（临时 index，不污染 agent 暂存）
     │        记录 (ticket,round,tree,base,target)；采集完整性校验
     ▼
build   ──── 固定 identity/date 造 dangling commit（确定性 SHA）
     │        用 gate ref 钉住防 gc
     ▼
review  ──── 外部引擎审该 commit → 归一化 findings → GatePolicy 判 pass/reject（fail-closed）
     │
     ├── reject ─▶ 结构化 findings 回喂，round+1，退回 presubmit
     │
     ▼ pass
publish ──── 写 publish_intent（WAL，先于任何不可逆步骤）
     │        签发 approval 记录（绑定 ref,old,new,tree，单次）
     │        push --push-option=gate-approval=<id>
     ▼
pre-receive ─ 现场重算 tree + 校 8 条件 + 消费 approval → 接受/拒绝
```

**关键顺序修正**：先 `commit-tree` 造出 dangling commit **再** review。原因：(1) 实测的两个引擎（prism/local-review）都 shell 调 live git，只能对「真实存在的 commit / 分支 / 暂存区」工作，无法审一个游离的 tree 对象；对 dangling commit 用引擎的 commit 模式（`git diff <sha>~1 <sha>` / `git show`）实测可行。(2) commit SHA 是 review 与 publish 的稳定锚点。

### 3.2 presubmit：固化 tree（实测采集规范）

```
# 用一个全新空的临时 index，不 read-tree HEAD（避免继承 skip-worktree/assume-unchanged 位）
GATE_IDX=<gate-home>/idx/<ticket>-<round>
GIT_INDEX_FILE=$GATE_IDX git -C clones/<ticket> \
  -c core.autocrlf=false -c core.safecrlf=false \
  add -A
GIT_INDEX_FILE=$GATE_IDX git -C clones/<ticket> \
  -c core.autocrlf=false \
  write-tree                                   → tree_hash（不可变）
# 用完删除 $GATE_IDX
```

- **不污染 agent 暂存区**：实测证明临时 index 方案下，agent 的真实 index 在采集前后完全一致。
- **钉死 `core.autocrlf`**：实测同字节在 `false`/`true` 下产出不同 tree_hash。固化与 publish 前复算必须用同一显式配置，否则 TOCTOU 复核会误判。
- **base_commit**：取 `auth.git` 中 `refs/heads/<target>` 的当前 tip；clone 的该分支必须正好在此 commit，落后则拒绝 presubmit（退出 12，`BASE_STALE`）。
- **空 diff**：`tree_hash == base_commit^{tree}` → 拒绝，且**不消费轮次**（实测 commit-tree 不会拦空 diff，必须应用层显式判）。

### 3.3 采集完整性校验（闭合 `.gitignore` 隐形漏洞）

`git add -A` 受 `.gitignore` 支配，而 `.gitignore`、`.git/info/exclude`、`core.excludesFile`、`filter.*.clean` 均可被 agent 控制。危险子集是**不在 tree 里、因而 reviewer 看不到 diff** 的排除输入。规则（`capture_integrity`）：

| 规则 | 条件 | 结论 |
|---|---|---|
| R1 | `.git/info/exclude` 非空 | BLOCKER，拒 presubmit |
| R2 | `core.excludesFile` 被设置 | BLOCKER，拒 presubmit |
| R3 | 存在 `filter.*.clean` 或 `core.hooksPath` | BLOCKER，拒 presubmit |
| R4 | 追踪的 `.gitignore` 指纹 != base 指纹 | WARNING，把 diff 呈给 reviewer |
| R5 | 忽略集（`git ls-files -o -i --exclude-standard`）相对 base 增长 | WARNING，路径清单记入审计 |

R1–R3 是对 clone 的廉价 preflight，闭合整个「隐形排除」类。**不用 `add -A --force`**——那会把构建产物/密钥强行入库，更糟。

### 3.4 review：调外部引擎（实测约束）

实测两个候选引擎均 shell 调 live git、无 stdin/文件 diff 输入路径、无 `GIT_INDEX_FILE` 支持。因此：

- 引擎对**已用 gate ref 钉住的 dangling commit** 工作（commit 模式）。这是 P2 接入时 adapter 必须适配的形态。
- `local-review` 的 `--json` 在 `review` 模式被忽略（只出 markdown），且引擎自身崩溃时它「放行 commit」——**与 fail-closed 相反**。adapter 必须包裹：引擎非零非「findings」退出 → 一律 reject。
- `prism` 退出码可区分 findings(`1`) 与崩溃(`2/3/4`)，JSON schema 已验证（§5 Finding 模型据此）。
- **S3 仍需实测 spike**：无法从文档断定引擎能否正确审「临时 index 造出的 tree 物化成的 dangling commit」。

### 3.5 publish 与崩溃恢复（见 §7 完整契约）

- **git 是最终真相**。`publish_intent` 先落库（WAL，`synchronous=FULL`）再做任何不可逆步骤。
- 发布态由查询 `auth.git` 的 ref 派生，匹配 **`commit_sha` 而非 `tree_hash`**（修正 `执行文档.md §3.5` 的静默放行 bug：不同 commit 可能 carry 相同 tree）。
- **删除 `执行文档.md §3.5` 的 `ambiguous → 人工裁决` 态**：bare 库在本地同一文件系统，push 结果任何时刻可零成本查询，不存在「不可确认的 push」。该人工态只会变成绕过自己闸门的逃生舱。

```
        └───────┬───────┘        └───────┬───────┘
```

### 4.2 禁止依赖（ArchUnit 强制，写成测试）

```
domain      依赖仅 JDK；禁止 import org.springframework..、org.eclipse.jgit..、java.sql..
application 依赖 domain、ports；禁止依赖任何具体 adapter
adapters    依赖 ports + 自身技术；禁止依赖另一个 adapter
cli/mcp     依赖 application；禁止任何模块反向依赖 cli/mcp
Spring 注解 仅允许出现在 adapters 与 config 装配层；domain/application 零 Spring
```

### 4.3 Maven 模块

单 Maven 多 module（`gate-domain` / `gate-application` / `gate-ports` / `gate-adapters` / `gate-cli`）。`gate-cli` 是唯一可执行 jar（Spring Boot repackage）。`domain`/`application`/`ports` 为纯 jar，`pom` 中不引入 `spring-boot-starter`。

### 4.4 Spring Boot 具体形态（决策 B）

```java
public static void main(String[] args) {
    SpringApplication app = new SpringApplication(GateApp.class);
    app.setWebApplicationType(WebApplicationType.NONE);   // 无 web
    app.setBannerMode(Banner.Mode.OFF);
    System.exit(SpringApplication.exit(app.run(args)));    // 经 ExitCodeGenerator
}
```

- picocli 经 `picocli-spring-boot-starter`；`IExecutionExceptionHandler` 映射到 §8 退出码表，`default → 70`。
- 日志只走 **stderr**；**stdout 是 JSON 通道**，退出前 flush（Spring + `System.exit` 否则会截断）。
- 持久层用 `JdbcTemplate` + `TransactionTemplate`，**不用 JPA**（三张表）。
- 仅**构造器注入**，无字段注入、无 `@Autowired`、domain 包不做 component-scan——保证 Spring 只是装配细节，决策可逆。
- **绝不从 `pre-receive` 里回调 JVM**：hook 是纯 `sh`，启动 JVM 太慢且违背 §1.3 收口。
- 代价诚实记录：JVM+Spring 每次启动 ~0.7–2s、fat jar ~30MB。对每工单调用几次的闸门可接受；若延迟成问题，逃生路径是常驻 daemon + 瘦客户端或 AppCDS，均不动架构。

## 5. 核心端口与领域类型（完整 Java 签名）

### 5.1 端口切分总则

> **R-PORT**：一个端口只有在「两个生产实现之间的行为差异不可能导致误放行」时，才允许有多个生产实现。

推论——**不设 `GitBackend` 端口**。闸门的全部正确性主张是「我审的 tree 就是落地的 tree」，该等式由 presubmit 算树、publish 复算、hook `rev-parse` 三方评估，而 hook 只能是 C git。若 presubmit 用 JGit 算树，就有两套 `.gitattributes`/`autocrlf`/mode/symlink/ignore 实现决定核心不变量，分歧会在 Windows CRLF 上首先爆发（实测 autocrlf 影响 tree_hash 已证）。因此**树计算、造 commit、push 全部钉死真实 `git` 二进制**，测试缝在 `ProcessRunner`，不在 git 语义。

**S4 因此不再是阻断 spike**：不问「JGit 能否发 push-option」，因为不让 JGit 碰权威路径。降级为 P2 之后的可选优化，无双路线。JGit 若保留，仅用于只读、非权威的便利操作（log 渲染、报告里的 ancestry），或干脆不引入。

```java
    BlobRef rawOutput, int exitCode, java.time.Duration duration

}

public record EngineFailure(
    EngineDescriptor engine, FailureKind kind, String detail, int exitCode
) implements ReviewEvidence {
    public <T> T accept(EvidenceVisitor<T> v){ return v.visit(this); }
    public enum FailureKind { TIMEOUT, CRASH, UNPARSEABLE, MISSING_FIELD, COVERAGE_GAP }
}

/** 统一 Finding（据 prism 已验证 schema + 各引擎差异的超集，§见调研）。 */
public record Finding(
    Severity severity,        // 闭集：BLOCKER|WARNING|NIT|INFO
    String rawSeverity,       // 原样保留供审计（prism: low/med/high；local-review: nit..critical）
    String path,              // 仓库相对，'/' 分隔，绝不绝对路径
    Integer lineStart, Integer lineEnd,   // 行区间；单行则 end=start
    String ruleId,            // 可空——prism 只有哈希 id，无稳定规则词表
    String message, String suggestion
) {}

public enum Severity { BLOCKER, WARNING, NIT, INFO }
```

**三条让「加第二个引擎零 core 改动」的约束**：
1. **端口返回证据，绝不返回 verdict**。退出码是证据。只有 `GatePolicy` 产 verdict。引擎自报 `{"verdict":"pass"}` 只能当数据。
2. **`coveredPaths`**：core 断言 `coveredPaths ⊇ changedPaths(base, tree)`，缺口即 reject。否则引擎静默跳过 binary/超大/失败分块的文件 → 对未审内容放行，且全程无异常。
3. **未知 severity 映射到 `BLOCKER`，`degraded=true` 强制 reject**。默认拒发生在映射表里，不在调用方。severity 映射表按引擎独立配置（严禁假设共享词表——prism `low/med/high`、local-review `nit/info/warning/major/critical`、codereview-mcp `CRITICAL/WARNING/SUGGESTION/NOTE` 各不相同）。

## 6. pre-receive 完整契约与放行凭据（实测通过）

### 6.1 令牌方案（推翻 `执行文档.md §3.4` 的「tree 即令牌」）

`执行文档.md §3.4` 断言「令牌 = `tree=<tree_hash>`，天然防重放」。**实测证伪（B9）**：客户端无需伪造等式，诚实算出自己未审 commit 的 tree 即满足 `GIT_PUSH_OPTION_0 == recomputed(tree)`，hook 放行，未审代码入库。原矩阵只测了「攻击者忘带/带错 option」，从未测「攻击者带对自己 tree 的 option」。且这正中真实威胁：LLM 会照抄文档里的 push 命令。

**正式方案（实测 B9/B15/B16/B18/B19 全 REJECT）**：签发一个服务端 approval 记录，push-option 只携带**非机密 id**（`/proc/<pid>/cmdline` 全局可读，绝不把机密放 argv），授权来自「记录存在 + 精确绑定 + 单次消费」，由文件系统保护。

### 6.2 approval 记录

`issue()` 在 `<gate-home>/approvals/<id>` 写入（`id` = 128-bit 随机 hex），内容逐行：

```
ref=refs/heads/main
old=<base_commit>       # 精确绑定该次 ref 转移的起点
new=<commit_sha>
tree=<tree_hash>
```

- 绑定 `old` 闭合**快照洗白（B15）**：把已审 tree 嫁接到不同 parent 会静默回滚中间所有改动，只校 tree + fast-forward 都拦不住，必须校 `parent==old`。
- 单次消费：hook 校验通过后 `mv approvals/<id> approvals/consumed/<id>`，两个并发 push 抢同一 id 只有一个 rename 成功。
- approval 目录在 `auth.git` **之外**，路径烘焙进生成的 hook——这是日后能加 OS ACL 拿到真实边界的唯一位置，无需重构。

### 6.3 pre-receive 完整脚本（8 条判定，全部实测）

```sh
#!/bin/sh
set -eu
APPROVALS='<烘焙的绝对路径>/approvals'
[ "${GIT_PUSH_OPTION_COUNT:-0}" = "1" ] || exit 1              # ① 恰好一个 option
case "${GIT_PUSH_OPTION_0:-}" in gate-approval=*) ;; *) exit 1 ;; esac
id=${GIT_PUSH_OPTION_0#gate-approval=}
case "$id" in *[!0-9a-f]*|"") exit 1 ;; esac                   # ② 字符集，防路径穿越
rec="$APPROVALS/$id"; [ -f "$rec" ] || exit 1                  # ③ 记录存在（未消费）
lines=0
while read -r old new ref; do
  lines=$((lines+1)); [ "$lines" -eq 1 ] || exit 1             # ④ 单 ref 更新
  [ "$new" != "0000000000000000000000000000000000000000" ] || exit 1  # ⑤ 拒删除
  [ "$(git cat-file -t "$new")" = "commit" ] || exit 1
  tree=$(git rev-parse --verify "$new^{tree}") || exit 1       # 现场重算，不信客户端
  parent=$(git cat-file -p "$new" | sed -n 's/^parent //p')
  [ "$(printf '%s' "$parent" | grep -c .)" = "1" ] || exit 1   # ⑥ 单 parent（拒合并）
  grep -qx "ref=$ref"     "$rec" || exit 1
  grep -qx "old=$old"     "$rec" || exit 1
  grep -qx "new=$new"     "$rec" || exit 1
  grep -qx "tree=$tree"   "$rec" || exit 1                      # ⑦ 精确绑定四元组
  [ "$parent" = "$old" ]  || exit 1                             # 闭合 B15 快照洗白
  case "$ref" in refs/heads/main) ;; *) exit 1 ;; esac          # ⑧ ref 白名单
  if [ "$old" != "0000000000000000000000000000000000000000" ]; then
    git merge-base --is-ancestor "$old" "$new" || exit 1        # fast-forward
  fi
done
[ "$lines" -eq 1 ] || exit 1                                    # 拒零 ref
mv "$rec" "$APPROVALS/consumed/$id" || exit 1                    # 单次消费
exit 0
```

- `git rev-parse "$new^{tree}"` 取代 sed 管线（无外部工具、无空串陷阱）。
- `auth.git` 侧配置：`receive.advertisePushOptions=true`（否则 push 发不出，preflight 硬检查）、`receive.denyDeletes=true`、`receive.denyNonFastForwards=true`。
- hook 内容哈希登记进审计日志，**每次 publish 前**校验，不只启动时（§10）。hook 逻辑保持最小且生成，不读任何 agent 可控的配置。

### 7.3 幂等键裁定

`(ticket_no, review_round, tree_hash)` 作为**意图唯一约束充分**，作为**唯一身份不足**：
- agent 回退到旧状态 → 同 tree_hash 不同 round → 区分。
- 两工单同 tree → 不同 ticket_no → 区分（且 commit message 含 ticket，SHA 也不同）。
- 空 diff（tree==base_tree）→ 不是幂等问题，是缺前置：presubmit 显式拒，不消费轮次。
- 补 `UNIQUE(commit_sha)`：`commit_sha` 是效果身份。二次 publish → intent 行已有 commit_sha → push 变 no-op / 已是 ancestor → 返回原结果。

### 7.4 崩溃点与恢复（不变量）

| 崩溃点 | 已落持久态 | 恢复动作 | 有歧义? |
|---|---|---|---|
| C0 意图写入前 | 无 | 从 presubmit 重来 | 否 |
| C1 意图已写，复算 tree 前 | intent `PENDING` | 重跑；复算 tree 比对 | 否 |
| C2 tree 校验，commit-tree 前 | `PENDING` | 重跑；commit-tree 幂等（同输入同对象） | 否 |
| C3 commit 存在，push 前 | `PENDING`+`commit_sha` | 查 auth ref → 不在 → push | 否 |
| C4 push 中（对象已送，ref 结果未知） | `PENDING`+`commit_sha` | 查 auth ref 判定 | 否 |
| C5 push 已收，DB 更新前 | auth ref 已移 | 查 auth ref → `PUBLISHED` | 否 |

**发布态派生函数**（回答「是否已发布」的唯一合法方式）：

```
published(intent) :=
  intent.commit_sha != null AND
  git -C auth.git merge-base --is-ancestor <commit_sha> refs/heads/<target> == 0
```

匹配 `commit_sha`，**绝不匹配 `tree_hash`**（修正 `执行文档.md §3.5`）。

**不变量**：
- **I1** — `publish_intent` 行先落库（`synchronous=FULL`）再 `commit-tree`，且钉死 author/committer/date（否则 SHA 不可复现，I1 崩塌）。
- **I2** — 只有 `status`/`commit_sha`/`observed_*`/`finished_at` 可更新，其余插入后不可变。
- **I3** — **任何 SQLite 事务都不得跨 `ProcessBuilder` 调用**。
- **I4** — **DB 永不是权威**。丢任何发布路径上的行只增加重复工作（重审），绝不产生误放行、绝不阻断恢复；一切可从 `auth.git` + 审计日志派生。
- **I5** — committer = 闸门固定身份（`gate <gate@localhost>`），author = 工单/agent 身份，date 钉固定 epoch；均经环境变量设定，绝不继承用户 config。trailer（`Ticket:`/`Tree:`/`Reviewed-By:`）是**声明**，同权限 agent 可伪造，文档需明示。

## 8. 状态机、错误模型、退出码

### 8.1 工单状态机（实现约束）

| # | From | To | 触发 | 前置 |
|---|---|---|---|---|
| T1 | 待处理 | 进行中 | 编排层/人 | clone 已建，分支在 base_commit |
| T2 | 进行中 | 预提审 | agent（唯一可触发的转移） | 工作区非空，capture_integrity 通过，tree!=base_tree |
| T3 | 预提审 | 审核中 | 系统 | dangling commit 已造并钉 gate ref |
| T4 | 审核中 | 已驳回 | 系统（GatePolicy，非 agent） | 产出结构化 findings |
| T5 | 已驳回 | 进行中 | 系统（回喂后自动） | review_round += 1 |
| T6 | 审核中 | 待提交 | 系统（GatePolicy，非 agent） | verdict == PASS |
| T7 | 待提交 | 已完成 | 系统 | commit_sha 经 published() 判定在目标分支 |
| T8 | 审核中 | 需人工 | 系统 | binary/超大/coverage 缺口 |
| T9 | 任意非终态 | 已取消 | 人 | — |

终态仅 `已完成`/`已取消`。agent 只能触发 T2——这是 §5 权限域的依据。

### 8.2 fail-closed 的结构保证（决策 C 的落地）

让「放行能力」成为一个只有 policy 能铸造的值，「忘记检查」在类型系统中不可表达：

```java
public final class PublishAuthorization {     // 无 public 构造器
    private PublishAuthorization(/*...*/) {}
    static PublishAuthorization mint(/*...*/){ /*...*/ }  // 包私有，仅 GatePolicy 调
}

public final class GatePolicy {
    public Decision decide(ReviewEvidence e, Snapshot s, Policy p) {
        return e.accept(new EvidenceVisitor<Decision>() {
            public Decision visit(EngineReport r) {
                if (r.degraded()) return Decision.reject(FailureKind.CRASH);       // 默认拒
                if (!coversAll(r, s)) return Decision.reject(FailureKind.COVERAGE_GAP);
                Severity worst = worst(r.findings(), /*未知→BLOCKER*/);
                return switch (p.strictness()) { /* BLOCKER→reject；其余按配置 */ };
            }
            public Decision visit(EngineFailure f) { return Decision.reject(f.kind()); }  // 一切失败→拒
        });
    }
}

// publish 无 ALLOW 决策不可达
PublishResult publish(PublishCommand c, PublishAuthorization auth);
```

- adapter 的 `review()` 声明不抛异常，其体是唯一的 `try{...}catch(Throwable t){ return new EngineFailure(...); }`——超时/崩溃/坏 JSON/缺字段/引擎消失全部变成 sealed 类型的**值**。
- Java 17 的 `switch` 模式仍是预览，穷尽不由编译器保证；故用 sealed 接口上的 visitor 抽象方法——加第三个子类型会**编译失败**直到每个消费方处理它。
- F5（引擎二进制缺失）是**启动**检查（§10），不是 review 期分支：直接拒绝启动。

### 8.3 退出码表（编排层/shell 消费）

`0` 必须只意味着「可以继续」。reject 高频但不是成功。但必须与闸门故障可区分，好让编排层重试故障、回喂驳回。

| 码 | 含义 | 调用方动作 |
|---|---|---|
| 0 | PASS / 放行 | 继续 |
| 10 | REJECT — 审核 findings（blocker） | 回喂 findings，agent 修，新一轮 |
| 11 | REJECT — TOCTOU / tree 不一致 | 重新 presubmit |
| 12 | REJECT — 前置（base 移动/非 FF/空 diff/ref 非白名单/合并进行中） | 重新同步 + presubmit |
| 13 | REJECT — 需人工（binary/超大/coverage 缺口） | 升级人工 |
| 20 | GATE_ERROR — 引擎失败（超时/崩溃/不可解析/degraded） | 可重试；对该 ref 视同拒 |
| 21 | GATE_ERROR — git/IO/锁忙/DB | 可重试 |
| 22 | GATE_ERROR — 配置错误（hook 漂移/advertisePushOptions 关/引擎缺失） | 运维修，勿重试 |
| 64 | USAGE（参数错，sysexits EX_USAGE） | 修调用 |
| 70 | 内部不可达（sysexits EX_SOFTWARE） | 报 bug |

保留 `1` 不主动发；避开 `2` 与 ≥125。机器输出 JSON 到 **stdout**（含 `schema_version`）；人类文本到 **stderr**。单一 `System.exit` 调用点在 CLI adapter，`default → 70`，退出前 flush。

### 8.4 静默放行可能藏身处（逐一封堵）

1. 「tree 即令牌」的同义反复 → §6 approval 方案。
2. hook 只读一行 stdin 而 git 对全部 ref 施用退出码 → §6.3 判定④循环全部 ref。
3. hook 空串比较（删除/非 commit 使 `$tree` 空）→ `set -eu` + `--verify` + 非空断言。
4. 引擎 coverage 缺口 → `coveredPaths ⊇ changedPaths` 断言。
5. 空 review 输入（错 base/CRLF-only diff）→ 断言 diff 非空且源自同一 tree_hash。
6. adapter catch 返回空 findings 列表 → `EngineFailure` + `degraded`。
7. reconcile 匹配 tree_hash 而非 commit_sha → §7.4 修正。
8. 引擎全出 warning + 「仅 blocker 拒」策略 → 启动断言所选 adapter 能产 BLOCKER，并记 severity 直方图。
9. 进程超时死锁（满管道缓冲阻塞读使 `waitFor(timeout)` 永不触发）→ stdout/stderr 引到文件，再 `waitFor` + `destroyForcibly` + 收割子孙进程。
10. agent index 里 `skip-worktree`/`assume-unchanged` 藏文件 → §3.2 全新临时 index。

## 9. 锁与并发

### 9.1 锁粒度（修正 `执行文档.md §3.6` 的过粗）

独立 clone（§2.2）后，实际竞争面收窄：

| 操作 | 共享态 | 竞争? | 锁 |
|---|---|---|---|
| clone A/B 的 write-tree | 各自 index+ODB | 否 | 无 |
| diff 采集、引擎调用 | 各自工单文件 | 否 | 无 |
| clone 创建/删除 | 读不可变 auth 对象 / 各自目录 | 否 | 无 |
| commit-tree | clone 本地 ODB | 否 | 无 |
| **push → auth.git ref 更新** | `refs/heads/<t>`、`packed-refs` | **是**（check-then-act：old==base 后移动） | **按 `(project, ref)`** |
| approval 签发/消费 | approvals 目录 | 是 | 原子 FS 操作，非锁 |
| SQLite 写 | db 文件 | 是 | 单写连接 |

并发上限 4（`执行文档.md §3.6`）是**资源护栏**（LLM 成本、CPU），非正确性机制——文档需写明，防日后有人靠调低它「修」正确性 bug。

### 9.2 Windows 机制

`FileChannel.tryLock()` 于锁文件，**永不删除锁文件**：

```java
ReentrantLock jvmLock = locks.computeIfAbsent(key, k -> new ReentrantLock());
jvmLock.lock();
try (FileChannel ch = FileChannel.open(lockPath, CREATE, READ, WRITE);
     FileLock fl = ch.tryLock()) {           // null => 忙 => 快速失败，不自旋
    if (fl == null) throw new GateBusyException(key, readOwnerHint(lockPath));
    writeOwnerHint(lockPath, pid, host, op, Instant.now());   // 仅诊断
    body.run();
} finally { jvmLock.unlock(); }
```

- Windows 上 `FileLock` 是**强制锁**（OS 级），进程死亡时 OS 自动释放——**没有陈旧锁问题，不需要 PID/心跳/超时回收**。删除 `执行文档.md §3.6` 的 `.lock` + 陈旧锁超时清理设计。永不按 PID 回收 → 回收的 PID 结构性无关。
- 进程内锁必须**包住** `FileLock`：同 JVM 两线程锁同一文件会抛 `OverlappingFileLockException` 而非阻塞。
- `.owner` 边车仅用于错误消息，永不据它决策。
- preflight 拒绝 UNC/网络路径与已知云同步目录（OneDrive/Dropbox）——`FileLock` 与原子 rename 在那里语义不可靠，同步器会损坏 `.git`。

### 9.3 锁顺序（不变量 R-LOCK）

> 严格按此顺序，永不倒置：(1) 进程内 `(project,ref)` 锁 → (2) `FileLock` → (3) SQLite 写事务。SQLite 事务绝不跨 `ProcessBuilder` 或锁获取。结构性强制：事务 helper 只接受一个「纯 DB」函数式接口，`ProcessRunner` 无法注入其中。

git 锁恒在 DB 事务之外，无环，死锁问题消失。

### 10.1 配置（fail-closed 亦适用于配置）


### 10.1.1 LLM 供应商与模型（不装 Ollama，全部经 newapi 中转）

**决策**：本机不装 Ollama。所有 LLM 经自建 newapi 网关中转（`https://newapi.sakta.top`，OpenAI 兼容）。交互逻辑参考 opencode 的供应商配置：**先配供应商，再拉取该供应商的模型清单，系统对外暴露的是 `provider_id` + `model_name`**，不暴露 base_url / key。

数据模型（落库，见 §7.2 `provider` / `model` 两表）：

| 概念 | 说明 |
|---|---|
| provider | 一个 OpenAI 兼容端点条目：`{ id, name, base_url, api_key(仅存引用/加密), type }`。默认一条指向 newapi 网关 |
| model | 从供应商拉取（`GET {base_url}/models`）并缓存的模型：`{ provider_id, model_name, pulled_at }` |
| 对外契约 | 工单 / 审核记录只引用 `(provider_id, model_name)`；base_url / key 绝不进工单表、审计 trailer、日志 |

prism adapter 的映射（`prism` 本身是 OpenAI 兼容客户端）：

```
prism review commit <sha> --parent <base> --format json --fail-on none \
  --provider openai \
  --model <model_name>
env: OPENAI_BASE_URL=<provider.base_url>   # 指向 newapi 网关
     OPENAI_API_KEY=<provider.api_key>     # 从 provider 条目注入，不落 argv
```

- `--provider openai` 是**协议族**（OpenAI 兼容），不是 provider 条目——真正的 endpoint 由 `OPENAI_BASE_URL` 决定，指向 newapi。
- key 经**环境变量**注入，绝不进 argv（`/proc/<pid>/cmdline` 全局可读，同 §6.1 令牌原则）。
- 执行模型（agent CLI 用）与审核模型（prism 用）**各自独立选 `(provider_id, model_name)`**，二者相同时告警（审核员独立性，立项 §7.1）。
- `EngineDescriptor`（§5.3）记录审核所用 `(provider_id, model_name)` + argv 指纹，随 `review_result` 落库，供 §7 成本埋点与历史可比。
- **首次拉取模型清单是一次显式动作**（`gate provider pull <provider_id>`），不在每次审核时隐式拉——避免网络抖动阻塞闸门。清单缓存进 `model` 表，过期由人工重拉。

### 10.2 可观测

- 每次闸门决策一行结构化 JSON，关联 id `(ticket, round)`。
- `audit.jsonl` **哈希链**（每行 `prev_hash`），编辑与截断可检测，应用永不轮转。链头副本可存项目目录之外以抵御蓄意编辑。

| 检查 | 失败 |

| `hooks/pre-receive` 存在、可执行、**内容哈希 == 生成哈希** | 22 |

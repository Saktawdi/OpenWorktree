**一句话横向定位**
- **Multica**：最新、最“AI 原生”的看板，本质是**“给 AI agent 用的看板/工作台”**，前端是 React（Next.js + Electron + Expo/iOS）多端共享，与 gate 的“agent 自主干活的工单系统”最神似。
- **Plane**：最成熟、最“工程化”的**人类团队项目管理**，视图丰富、社区体量最大，是工单详情/多视图/交互细节的最佳参考。
- **Wekan**：最“简、老、稳”的**传统看板交互**（拖拽、列卡、泳道），代码与视觉都最朴素，可作为经典看板交互基线。

## ④ 前端原型参考建议（针对 gate-web-ui）

> gate-web-ui 现状已探明：Vue 3 + Vite + Pinia + Vue Router + **naive-ui**，**暗色云平台风**（深底 `#09090b`、主蓝 `#0c5cab`、卡片面 `#0f0f12`、边线 `#1f1f23`、数字用 IBM Plex Mono），已实现 S0（登录 + 首页项目看板空壳 + 侧栏：工单看板/审核台/会话/成本）。规划：S1 工单看板（**9 阶段状态机 → 8 列看板**，PENDING/IN_PROGRESS/PRESUBMITTED/IN_REVIEW/READY_TO_PUBLISH/NEEDS_HUMAN/DONE/CANCELLED，其中 REJECTED 回流并入 IN_PROGRESS 列并标红、DONE/CANCELLED 折叠为窄列）；S2 工单详情 + 审批流（review/publish 为 **202 + task_id + SSE 进度**的异步任务）。

### ④.1 项目维度设计点

**Multica（AI-native 看板，最贴合 gate“agent 干工单”语义）**
- **信息架构**：侧栏分组导航 + 多 workspace/tab 语义；把“人 + agent”都当作**可指派主体**显示在卡片/看板上 —— gate 的工单卡片应同样承载“执行者=agent”的信息（agent 名称/运行状态）。其"Inbox"/"审核台"分流（只在 agent 需要人介入时才 ping 人）与 gate 的 “审核台”导航高度同源，可作为该页的信息架构样板。
- **看板交互**：卡片可展示**执行痕迹（run/execution log、token 用量）**与**审核门（review gate）**等过程态而不只停留在“列上移动” —— gate 的工单详情/审批流可借鉴“把一次 agent 执行会话当作可回放、可附属于工单的一等公民”的交互。
- **视觉风格**：本地代码证实其为**深色 + 语义 token + 角色化字阶**（`page-canvas/foreground、text-title/text-body/caption`）的现代 cloud-style；**tab 组 + 独立工单窗口（master-detail 弹层）+ modal registry + 命令面板（⌘K 搜索）+ 浮动 chat** 的组合，是偏“工作台/IDE 感”而非“后台管理系统”的质感 —— gate 若想走“云平台工作台”风可借鉴这种**多层 shell（固定工具条 + 可折叠侧栏 + 主画布留浮边）**。
- **组件模式**：React Query（服务端）＋ Zustand（视图态）双 store 分离、乐观更新仅在“可预测、不跳页”处用 —— gate 的 Pinia 通信模式可照此划分“服务端数据 vs 视图态”。UI 用 shadcn 原子 + lucide 图标 —— 对应 gate 用 naive-ui + 统一图标库。
- **注意**：Multica 许可证对复用 UI **限制最严**，且代码不可直接抄用 → 只做**交互/信息架构蓝本**，全部自研。

**Plane（最工程化、视图最丰富，最适合“工单详情 + 多视图”）**
- **信息架构**：工单（Issue）/迭代（Cycle）/模块（Module）三维组织，与 gate 的工单+看板+审核台可以互通；**工单详情页的信息密度与分组布局**（标题、状态机、优先级、指派、描述、活动时间线、关联 PR/commit）是业界标杆，非常适合作为 gate **工单详情页**的结构参考。
- **看板交互**：**多视图切换**（列表/看板/日历/甘特）是 Plane 强项；gate 至少应做**看板列拖拽换列（跨列）**与**列表⇄看板视图**，借鉴其“列头聚合计数、卡片字段精简显示、拖拽即时落库”的交互。其状态机驱动列 + 少量非终态列，可对照 gate 的 9 阶段状态机设计更轻量的列呈现。
- **视觉风格**（推断，基于其公开界面）：现代浅色/通配默认的 SaaS 项目管理风，卡片留白充足、信息密度高但克制 —— 可以给 gate 做“**高信息密度下的排版与分组节奏**”参考，但 gate 若要保留暗色云平台风，需自行转成暗色 token。
- **组件模式**：组件/页面/hooks 分层清晰、复用度高 — React Router + Vite（v1.2 起）。gate 用 Vue Router + naive-ui，可借鉴其“**详情页可深链（/issues/:id）+ 看板状态可 URL 化**”的路由设计，便于审批流回跳与分享。
- **注意**：**AGPL 传染最烈，组件源码一律不要复制**；只参考结构、交互与信息设计。

**Wekan（经典看板，最适合“看板列+卡片+拖拽”基线）**
- **看板交互**：Trello 式**列+卡拖拽、泳道、卡片标签/到期日/清单/附件**是成熟到“被行业抄烂”的范式 —— gate 的 8 列看板应**优先对照 Wekan** 确定“行的拖拽换列、卡片内字段展示、列内排序、泳道（如按 agent 分泳道）”等最基础的可用性细节。
- **视觉风格**：最朴素（Meteor+Blaze 老栈配经典 Trello 卡片），**不建议 gate 直接借鉴其视觉**，仅将其作为“交互基线”审视：确认 gate 没有遗漏看板用户熟悉的心智。
- **组件模式**：老式 jquery-ui sortable 拖拽 —— **不值得跟随**技术选型，仅确认“拖拽是该看板的核心交互”。
- **许可**：MIT，三项目中**唯一允许直接复用代码** —— 若 gate 想快速落地某段看板 CSS/交互逻辑，Wekan 是“可安全抄”的唯一来源（避开其 GPL 插件）。

### ④.2 首选参考组合（结论）

**主参考：Plane** —— 作为 gate 前端设计的**第一参照系**。理由是：① 体量最大、最成熟（55.9k stars）、社区活跃稳定、可持续跟进；② 它的本质是“人类的工程团队工单/项目管理”，与 gate 的“工单看板+工单详情+审批流”**覆盖面最重合**，尤其 **Plane 的工单详情页（Issue Detail）信息架构、状态机驱动的多视图看板、列表⇄看板切换、以及被业界长期打磨的卡片密度与排版节奏**，几乎每一项都直接命中 gate 要做的页面。具体借鉴：**工单详情页**（标题/状态机/指派/优先级/描述/活动时间线/关联 PR 的分组布局）、**看板多视图切换与列拖拽交互**、**URL 可深链的路由结构**。

**第二参考：Multica** —— 承担“AI-native 语义 + 工作台质感”补充。因为它与 gate “让 agent 干工单、人负责审核放行”的**业务语义最贴近**：卡片上体现“指派给 agent + 运行状态 + 审核门”，以及“Inbox/审核台把该人工介入的事集中到一处”的信息架构，是 gate 审批流与卡片体该重点借鉴的地方；其**多层 shell（工具条+侧栏+画布）、命令面板、独立工单窗口**的“云平台工作台”视觉方向也贴合 gate 暗色 wind 风的取向。**Wekan** 仅作“经典看板交互基线”，用于对照确认拖拽换列、泳道、卡片字段没有遗漏，若有可直接复用的 MIT 看板交互细节可安全采用。

> **落地建议**：以 **Plane 的工单详情 + 多视图看板**定信息架构与排版骨架，以 **Multica 的“agent 作为指派对象 + 审核台/Inbox + 工作台 shell”**定业务交互与视觉质感，以 **Wekan 的经典看板交互**兜底可用性；三者都**不得直接把源码复制进 gate**（Plane AGPL 传染、Multica 自定义商业/品牌条款均禁复用，仅 Wekan MIT 例外），所有设计最终均以 **Vue 3 + naive-ui + gate 自有的暗色云平台 token** 自行实现，再用 **OpenDesign** 出高保真原型。

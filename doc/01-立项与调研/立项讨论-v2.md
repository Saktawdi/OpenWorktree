## 0. 一句话定位

一个**本地运行的 Git 工单 + 强模型代码审核**系统。它以 MCP Server 形式暴露能力，让 vibe coding 工作流里"质量参差不齐"的环节——代码提交——被一个独立的强模型审核员卡住，**只有审核通过的那份快照**才允许进入权威 git 历史。

核心价值假设：**成本可控的质量闸门**。弱模型（执行 agent）便宜地干活，强模型（审核员）只在"预提审"这一步介入，用较低 token 成本守住代码质量底线。

> 注意：上面这句话在 v2 中被明确标记为**待验证假设**，而非既定事实。验证方法见 §1.3 与 §15。若度量结果显示审核成本逼近或超过执行成本，本项目的立项理由需重新评估。

> **后续进展补注（2026-08-14）**：本节描述的"一套本地 Git 工单系统"定位已在执行阶段收窄为"**一个 CLI 无关的 git 提交闸门层**"。v2 §0 的大系统愿景（工单 + 看板 + 终端 + 审核）由 multica / agtx / llmux 等项目覆盖，本项目只保留闸门层。详见文首「后续进展」A 节与 `../归档/done/执行文档.md §1.3`。

## 1. 背景与动机

### 1.1 问题

vibe coding 下，执行 agent 的代码质量层次不齐。让强模型全程参与每个工单成本太高；让弱模型自由提交又容易引入垃圾代码 / 安全漏洞 / 破坏构建。

### 1.2 洞察

审核是低频高价值动作。把强模型严格限制在审核节点，理论上成本可控且收益最大。

### 1.3 成本假设（v2 新增：必须验证，不得当作前提）

v1 写"95% token 花在写代码，只有 5% 该花在审代码"。这是断言，没有数据支撑，且存在明确反例：

- 强模型审一个中等 diff，需读 diff + 相关上下文文件，单轮几万 token 起。
- 若严格度设置不当导致反复打回 3 轮，**审核累计成本可以超过执行成本**。
- §17 自认的"diff 爆炸"风险正是这条的放大器。

因此 v2 把它降格为**待验证假设 H1**：

> **H1**：在真实工单分布下，`审核 token / (执行 token + 审核 token)` 的中位数 < 20%，且一次通过率 > 60%。

H1 的度量口径、埋点字段与判定时点见 §15。**H1 不成立则项目应缩减为一个 pre-commit LLM 检查插件**（见 §12）。

> **后续进展补注（2026-08-14）**：H1 首轮真实数据已收集（20 个工单样本）。**classification = PARTIAL**：first_pass_rate = 45%（落在 40%–60% 区间，未达 ESTABLISHED 的 >60% 也未触 REFUTED 的 <40%）；cost_ratio_median = NaN（degraded basis——prism 0.5.0 JSON 无 usage 字段，无法计算精确 token 占比）。H1 未证伪也未成立。详见文首「后续进展」E 节与 `../归档/done/h1-stage-report.md`。

### 1.4 约束

- 必须本地运行。
- 必须基于真实 git（不自造版本控制）。
- 必须能对接多种 LLM（执行模型可弱可强，审核模型必须强，且两者配置解耦）。

## 2. 核心工作流（v2 修订：加入 tree 固化与驳回回喂）

```
agent 领取工单
      │
      ▼
   进行中  ◀─────────────────────────┐
      │                              │
      ▼                              │
[预提审 presubmit_create]            │
  · 固化工作区为 git tree 对象        │
  · tree_hash + base_commit 落库     │
      │                              │
      ▼                              │
  审核中（锚定 tree_hash）            │
  人工 diff 复核  or  review_run     │
      │                              │
      ├──── 驳回 ────────────────────┤
      │     · 结构化行级评论回喂 agent
      │     · review_round += 1
      │
      └──── 通过 ───▶ 待提交
                        │
                        ▼
                 [commit_execute]
                  1. 复核 tree_hash 未变（不一致则退回预提审）
                  2. git commit-tree 提交该 tree
                  3. 携一次性令牌 push 至 bare 权威库
                     （pre-receive 在接收端校验令牌 + tree_hash）
                        │
                        ▼
                   工单 → 已完成
```

**铁律一（终态唯一入口）**：`已完成` 只能由「审核通过 → commit-tree → push 被 `pre-receive` 接受」这条路径到达。

**铁律二（v2 新增，闭 P0-3）**：审核对象是**不可变的 `tree_hash`**，不是 live 工作区。`commit_execute` 提交的必须正是被审核的那个 tree；若期间工作区变动导致重算 tree 不一致，**直接驳回并要求重新预提审**。

**铁律三（v2 新增，闭「驳回回喂」缺口）**：驳回不是终点，是系统日常最高频路径。驳回必须产出**结构化结果**（见 §7.3 schema），经 MCP 回喂给 agent 并把工单退回 `进行中`，`review_round` 自增。

- ~~`规模`（小/中/大）~~ — YAGNI，且"按行数自动估算"没有任何消费方。删除。

#### 3.2.1 状态机（v2 新增：v1 只列了状态名，没有转移表）

| # | From | To | 触发者 | 前置条件 |
|---|---|---|---|---|
| T1 | 待处理 | 进行中 | 人 / 系统调度 | worktree 与分支已创建 |
| T2 | 进行中 | 预提审 | **agent** | 工作区非空，tree 固化成功 |
| T3 | 预提审 | 审核中 | 人 / 系统 | `tree_hash` 已落库 |
| T4 | 审核中 | 已驳回 | **人 / 审核员模型（非 agent）** | 产出结构化驳回结果 |
| T5 | 已驳回 | 进行中 | 系统（回喂后自动） | `review_round += 1` |
| T6 | 审核中 | 待提交 | **人 / 审核员模型（非 agent）** | 结论 = 通过 |
| T7 | 待提交 | 已完成 | **系统** | tree_hash 复核一致 且 push 被 `pre-receive` 接受 |
| T8 | 任意 | 人工介入 | 监督系统（§8） | 命中异常规则 |
| T9 | 任意非终态 | 已取消 | 人 | — |

- **`已驳回` 不是终态**（闭 v1 细节问题），经 T5 回到 `进行中`。
- 终态仅 `已完成` / `已取消`。
- 表中「触发者」列**直接构成 §4.2 权限域的依据**：agent 只能触发 T2。

### 3.3 预提审 PreSubmit

- 关联一个工单 + 一个 `review_round`。
- **`tree_hash`（v2 核心新增）**：`git write-tree` 产出的不可变 tree 对象 ID，审核与 commit 的唯一锚点。
- `base_commit`、`target_branch`。
- 捕获范围：tracked 改动 + **untracked 文件** + 权限(mode)变更 + `.gitignore` 漂移（见 §6.3）。
- diff 全文落文件系统，DB 存路径 + 大小 + 哈希（见 §10.5）。
- 审核结论：通过 / 驳回（结构化，见 §7.3）。
- 通过后进入 `待提交`，**不直接 commit**。

### 3.4 终端会话 TerminalSession（项目 n 个）

- 绑定**工单的 worktree**（不是项目根目录）。
- 实时 stdout/stderr 流，落盘为原始流文件。
- 可被监督系统抽取关键信息（见 §8）。
- 两种开法：
  - **空白终端页**：用户手动新开，自行输入 CLI。
  - **agent 终端页**：系统一键新开并自动拉起 agent CLI，注入工单上下文（见 §3.5）。

### 3.5 agent 调度（B 模式：系统通过 MCP 驱动 agent）

**保持 v1 决策：采用 B 模式**——系统是 agent 的调度方与闸门，而非旁观者。

- 用户点「启动 agent 处理工单」→ 系统为该工单创建 worktree + 分支 → 新开终端页 → 自动执行 `opencode` / `claude code`（可指定执行模型）。
- **上下文注入**：工单号、需求描述、目标分支、约束（"你无权 push 到权威库"）以 prompt + MCP 配置形式注入。
- **agent 通过本系统 MCP 回写**，且**只能使用 agent 域 tool**（§4.2）。
- **强绑定**：工单 ↔ worktree ↔ 分支 ↔ 终端会话 四者生命周期绑定，便于审计与回滚。

> **v2 修正 v1 的一个错误推理**：v1 §10 称"因已定 hook 硬约束，CLI 回连 MCP 的可行性降级为非阻断"。该推理依赖"本地 pre-commit hook 是物理闸门"这一**错误前提**（见 §6.1）。修正后，agent CLI 能否注入自定义 MCP server 配置**重新升级为立项前必过 spike**（见 §16 S1）。

## 4. MCP Server 设计

### 4.1 传输（v2 重写，闭 P0-1）

**v1 的矛盾**：v1 §8 写"后端常驻服务 + 内嵌 MCP **stdio** server"，§9.2 定 stdio。这不成立——stdio 传输的语义是**客户端 spawn 服务端子进程**并用该子进程的 stdin/stdout 通信，天然 1:1 且生命周期由 client 掌控。常驻 Spring Boot 服务"内嵌的 stdio server"绑定的是它自己的 stdin/stdout，N 个 agent CLI 与 Vue 前端根本无法接入。

**v2 决策**：

- **主传输：Streamable HTTP / SSE**，`bind 127.0.0.1`，Bearer token 鉴权。天然支持多客户端，与 Vue 前端共用同一服务进程。
- **stdio 兼容退路**：对只支持 stdio 的 CLI，提供一个**极薄的 `stdio ↔ HTTP` bridge 可执行体**。每个 agent CLI spawn 一个 bridge 实例，bridge 持 agent 域 token 转发至常驻服务。这才是"stdio 兼容"的正确形态——bridge 是一次性子进程，常驻服务不是。

### 4.2 Tool 权限域（v2 重写，闭 P0-2）

**v1 的漏洞**：v1 §4 是一张扁平清单，agent 与 UI 共用同一 MCP server，因此 agent 连上来即拥有 `presubmit_review`（自己下审核结论）、`commit_execute`（自己放行）、`terminal_write`（任意命令执行 = shell 逃生舱）、`config_set`（改审核员模型）。agent 只需 `presubmit_review(pass)` + `commit_execute` 两次调用即可绕过整个闸门，v1 §6 声称的"审核员独立性"在机制层面完全没有实现。

**v2 决策：两个能力域，两套凭据，两个 endpoint。**

#### agent 域（低权，token 随 worktree 下发，仅限本工单）

| Tool | 约束 |
|---|---|
| `ticket_get` | 仅限自己绑定的工单 |
| `ticket_comment` | 只能追加，不能改结论 |
| `ticket_update_status` | **仅允许 T2（进行中 → 预提审）** |
| `presubmit_create` | 固化 tree，仅限自己的工单 |
| `presubmit_get_diff` | 只读自己本轮的 diff |
| `review_result_get` | 读取驳回意见（回喂用） |

#### 人 / UI 域（高权，会话 token 绑定浏览器会话）

| Tool | 说明 |
|---|---|
| `presubmit_review` | 下审核结论 |
| `review_run` | 调审核员模型。**绝不下放给 agent**——否则 agent 可反复刷审核直到蒙过 |
| `commit_execute` | 复核 tree_hash + commit-tree + 携令牌 push |
| `terminal_open` / `write` / `read` / `close` | 等价任意命令执行，仅人域 |
| `terminal_spawn_agent` / `agent_start_ticket` | 调度 agent |
| `project_*`（含 `delete`） / `config_*` | 项目与配置管理 |

> **绝不把 `terminal_write` 放进 agent 域**——那等于直接送出一个 shell，本文档所有上层约束立即作废。这是 v2 最不可让步的一条。

### 4.3 资源 / 订阅

- `git://project/{id}/tree`、`git://project/{id}/log` 作为 MCP resource，支持订阅变更。
- 二者均为**派生视图**（§3.1），不代表 DB 持久状态。

## 5. 非功能需求（v2 新增章节）

v1 完全缺失这一章，导致容量、并发、延迟都无判据。

| 维度 | M1 目标 |
|---|---|
| 使用者 | **单用户、单机、本地**。不做多租户、不做团队协作 |
| 并发 agent | 同一项目 **≤ 4** 个并行工单（各自 worktree）；跨项目不限 |

## 6. 安全与防绕过（v2 重写）

### 6.1 闸门模型（闭 P0-4）

**v1 的错误**：v1 §6 / §9.4 称本地 `pre-commit` hook 是"物理闸门，不依赖 agent 自觉"。这个判断不成立。agent 在终端里持有 shell，绕过只需一行：

- `git commit --no-verify`
- `git -c core.hooksPath=/dev/null commit`
- `rm .git/hooks/pre-commit`
- 走 plumbing：`hash-object` + `write-tree` + `commit-tree` + `update-ref`（完全不触发任何 hook）

本地 hook 里唯一 `--no-verify` 跳不掉的是 `reference-transaction`，但它同样被 `core.hooksPath` 关掉。**结论：本地 hook 是减速带，不是闸门。**

**v2 的目标重述**（重述之后正确设计就自明了）：

> 目标不是"agent 不能 commit"，而是 **"未审核代码不能进入权威历史"**。

**v2 结构性方案**：

| 层 | 内容 |
|---|---|
| 权威库 | **bare repo**（`authoritative_repo_path`），无工作区，agent 无任何理由访问 |
| agent 活动区 | 每工单一个独立 **`git worktree` / clone**，agent 在其中**可以随意 commit**，无所谓 |
| 服务端闸门 | 权威 bare 库安装 **`pre-receive` / `update` hook**——服务端侧 hook，客户端任何 flag（含 `--no-verify`）**都跳不过**，因为它在接收端执行 |
| 放行 | 仅 `commit_execute` 在审核通过后携带**一次性审核令牌**代为 push；`pre-receive` 校验令牌 + `tree_hash` 匹配，否则拒绝整个 push |

这样闸门是**结构性的**（agent 物理上不在权威库里，且唯一入口在接收端校验），而不是靠 hook 自觉。

**诚实声明（v1 缺失）**：单用户本地环境下，agent 与本系统**以同一 OS 用户、同等权限运行**。因此 agent 理论上仍可篡改本系统配置、伪造令牌、或直接对 bare 库做文件级写入。**不存在绝对隔离。** 要达到绝对隔离必须上 OS 级手段（独立系统用户 + 目录 ACL，或容器 / VM）。M1 范围内接受此残余风险，并通过 §6.5 审计留痕使篡改可被事后发现；容器化列入 M2 备选（§13.3）。

### 6.2 服务认证与同源校验（闭 P1-10）

**v1 的漏洞**：Web 应用 + `terminal_write` tool，若仅 bind 127.0.0.1 而无认证，则本机任意进程、以及用户浏览器打开的任意恶意页面（**CSRF / DNS rebinding**）都能驱动它执行任意命令。这等于对外提供了一个无认证 RCE 端点。v1 §6 完全没覆盖。

**v2 要求（全部为硬性）**：

1. `bind 127.0.0.1`，**绝不** `0.0.0.0`。
2. 启动时生成随机会话 token，写入仅当前用户可读的本地文件；所有 HTTP / WebSocket 请求必须携带。
3. 校验 `Origin` / `Host` 头白名单（抵御 DNS rebinding）。
4. WebSocket 握手同样执行 token + `Origin` 校验（易漏点）。
5. **两套独立凭据**：agent 域 token（随 worktree 下发、限定工单、可吊销）与人域 token（绑浏览器会话），对应 §4.2 两个 endpoint。

### 6.3 diff 完整性（闭 P0-3 + v1 遗留项）

- 预提审必须捕获：tracked 改动、**untracked 文件**、文件 mode（权限）变更、`.gitignore` 漂移、submodule 指针变更。否则 agent 可把脏东西塞进 repo 而不经审核。
- **TOCTOU 防护**：审核锚定不可变 `tree_hash`；`commit_execute` 先重算工作区 tree，与 `tree_hash` 不一致则拒绝并退回预提审（§2 铁律二）。
- 二进制 / 超大文件：单独列出，不送 LLM，强制人工确认。

> **后续进展补注（2026-08-14）**：v2 §2 铁律二（tree_hash 锚定）与铁律三（驳回回喂）均在 P1/P2 实现。但 v2 原文隐含的"令牌 = tree_hash 本身"被实测攻破（B9），见 §6.4 补注。

### 6.4 崩溃恢复与幂等（v2 新增，v1 缺失）

- **崩溃窗口**：`审核通过 → tree 复核 → commit-tree → push` 是多步过程，中途进程挂掉状态会悬空。
- **收敛规则**：以 **git 为最终真相**。启动时执行 reconcile：若 `tree_hash` 对应的 commit 已存在于权威库目标分支 → 工单置 `已完成`；否则回退到 `待提交`。
- **`commit_execute` 必须幂等**：以 `(ticket_no, review_round, tree_hash)` 为幂等键；重复调用不产生第二个 commit。
- 一次性审核令牌**用后即焚**，防止重放。令牌语义对齐 `gitproxy`（§12.4）：单次使用、仅内存持有、**仅在上游确认接受后才消费**、绑定 `(ref, tree_hash)`、超时自动失效。

> **后续进展补注（2026-08-14）**：v2 此处"令牌 = `tree=<tree_hash>`、天然防重放、少一张表"的设想**被 B9 攻破**——agent 可诚实算出自己未审 commit 的 tree 当令牌直接 push。实现阶段改为 **approval 记录方案**：绑定 `(ref, old, new, tree)` + 单次消费（`mv` 到 `consumed/`）+ `parent==old` 校验。B9/B15/B16/B18/B19 全部 REJECT。此外 v2 的"ambiguous 态"已删除（ADR-4），改为发布态查 auth ref 派生。详见文首「后续进展」D 节与 `../归档/done/spike-结论.md §2` / `架构落地执行文档.md §6`。
- **上游状态不明时不得静默重用令牌**：push 已发出但无法确认权威库是否接受 → 标记为 ambiguous，记日志并要求人工裁决，不自动重试。
- **fail-closed（v2 补充，来自 `claude-code-review-gate` 的经验）**：审核超时、崩溃、返回不可解析的结果 → **一律判为驳回**，绝不放行。唯一例外是审核引擎二进制缺失（此时根本没有闸门，应直接拒绝启动服务而非放行）。

### 6.5 审计留痕

- 每次放行记录：工单号、`review_round`、`tree_hash`、审核者（人 / 模型 ID + prompt 版本）、令牌 ID、时间。
- 写入 commit message trailer（如 `Reviewed-By:` / `Ticket:` / `Tree:`）**并**落独立审计日志文件（append-only）。
- 审计日志与 DB 分离存放，便于在 DB 被篡改时交叉比对。

## 7. 审核员设计（v2 新增章节）

### 7.1 独立性

- 审核模型配置与执行模型**物理解耦**（不同 provider 条目、不同 key 槽位），避免"自己审自己"。
- `review_run` 只在人域（§4.2）。agent 不能触发审核，也不能读取审核员配置。
- 系统在 UI 上显式展示"执行模型 X / 审核模型 Y"，若二者相同则告警。

### 7.2 diff 分块与聚焦（应对 §17 diff 爆炸）

- 超过 §5 体积阈值直接拒绝自动审核。
- 阈值内按文件分组，单文件超长则按 hunk 分块，逐块审核后汇总。
- 附带最小必要上下文（改动函数的完整定义、被改符号的直接调用点），而非整仓上下文。
- 增量审核：第 N 轮只送**相对第 N-1 轮的增量** + 上轮未解决的 blocker 列表。这是控制 H1（§1.3）成败的关键机制。

### 7.3 结构化结果 schema 与 prompt 版本（v1 缺失）

**问题**：审核 prompt 若随手修改，历史审核结论就不可比，也无法定位"是模型变差还是 prompt 变差"。

**v2 要求**：

- 审核 prompt 以**带版本号的模板**入库/入仓（`review_prompt@v3`），每条审核记录写入所用版本。
- 审核结果必须是**固定 JSON schema**（LLM 侧用 structured output / JSON mode 强约束），字段至少：

```
{
  "prompt_version": "review_prompt@v3",
  "verdict": "pass" | "reject",
  "findings": [
    {
      "severity": "blocker" | "warning" | "nit",
      "file": "src/x.java",
      "line_start": 42,
      "line_end": 47,
      "message": "...",
      "suggestion": "..."          // 可选
    }
  ],
  "summary": "..."
}
```

- **判定规则固定**：存在任一 `blocker` → `reject`；仅 `warning` / `nit` → 由严格度配置决定（可调 + 人工兜底）。
- 该 schema 同时是 §2 铁律三**回喂 agent 的载体**：驳回时把 `findings` 原样通过 `review_result_get` 交给 agent，agent 按行级定位修复。

## 8. 监督系统与并发控制

### 8.1 终端信息抽取（v2 降级：v1 的"轻量模型"移出 M1 范围）

**v1 问题**：v1 §7 提出用"规则 / 轻量模型"抽取终端信息。模型抽取会引入额外成本与误报，且**不在核心闭环上**。

**v2 决策**：M1 只做**纯规则（正则）**抽取：

- 构建失败 / 测试失败特征串
- 危险命令：`rm -rf`、`git push --force`、push 到非预期远端、`chmod 777`、`curl | sh`
- agent 卡死：N 分钟无输出
- token 消耗行（若 CLI 输出）

命中 → 按 §3.2.1 T8 转 `人工介入`。LLM 抽取推迟到 M2（§13.2）。

### 8.2 用途

人类同时监督多个并行 agent；异常时自动挂起工单，避免 agent 长时间空转烧钱。

### 8.3 git 并发与锁（闭 P1-8）

- **一工单一 worktree**（§3.2），从根上避免多 agent 互踩同一工作区。
- **项目级串行锁**：同一项目的 git 写操作（worktree 创建/删除、write-tree、commit-tree、push）串行化。JGit 不保证跨进程安全，锁需覆盖"本系统内多线程"与"外部 git 进程"两种来源（进程内锁 + `.lock` 文件 + 明确的超时与陈旧锁清理）。
- 并发上限见 §5。

### 8.4 生命周期清理（应对分支/worktree 爆炸）

- 工单进 `已完成` / `已取消` 后：终端会话关闭 → worktree `git worktree remove` → 分支按策略保留 N 天后删除。
- 孤儿 worktree / 分支由启动时 reconcile（§6.4）扫描并列入清理建议，**不自动删**（避免误删人类工作）。

## 9. 技术栈（沿用 v1 决策，补风险标注）

> 定位：可靠性 > 开发速度，选型围绕"强类型、可维护、易运维"。

### 9.1 后端与 MCP

- **后端**：**Java（Spring Boot）**。同时承载 HTTP/SSE MCP endpoint 与 Vue 前端静态资源。
- **MCP**：`modelcontextprotocol/java-sdk`，传输见 §4.1（**HTTP/SSE 主，stdio bridge 备**）。
- **进程模型**：常驻后端服务 + 每工单 agent 终端子进程 + 每 agent CLI 一个可选 stdio bridge 子进程。

### 9.2 Git 与存储

- **Git 操作**：**JGit** 为主（无需 spawn、行为可控、易测试）；`ProcessBuilder` 调真实 git 用于 JGit 覆盖不到的场景（hook 触发、`worktree` 子命令的边缘行为、`pre-receive` 侧验证）。
- **存储**：**SQLite** 主基座 + 大对象落文件系统（边界见 §10.5），配 **Flyway/Liquibase 迁移**（§10.6）。

### 9.3 前端与 LLM 接入

- **前端**：**Vue 3 + TypeScript（Vite）**。diff 用 Monaco / CodeMirror；类型契约经 OpenAPI 生成，避免手写 DTO 漂移。
- **终端**：`ProcessBuilder` + PTY 库（`pty4j` 等）spawn agent CLI；前端 **xterm.js**，双向流经 WebSocket。
- **LLM 接入**：provider 抽象层（OpenAI / Anthropic / 本地 Ollama），执行模型按工单可配，审核模型独立配置（§7.1）。

### 9.4 PTY 风险（v2 新增，闭 P1-9）

v1 把终端一句话带过，但这是选型里**最脆的一环**：

- `pty4j` / `java-pty` 需 JNI native 依赖；**Windows 走 ConPTY / winpty**，跨平台打包与排错成本远高于 v1 暗示的程度。当前开发环境为 Windows，此处坑最深。
- 不推翻"Java 优先"的决策，但**必须前置 spike**（§16 S2）验证：交互式输入、`Ctrl-C` 传递、窗口 resize、ANSI 颜色、**进程树整体 kill**（agent CLI 常派生子进程，杀不干净会留僵尸烧 token）。
- **降级预案**：若 spike 失败，"内嵌交互式终端"整块降级为**非交互式 spawn**（系统只以一次性命令方式调用 agent CLI，捕获 stdout/stderr，不提供可输入终端）。UI 的终端页退化为只读日志视图。该降级不影响核心闸门闭环。

| 10.8 | **权限模型**：MCP tool 分 agent 域 / 人域，两套凭据 | **v2 新增** | v1 扁平清单，agent 可自审自放行（§4.2） |

### 10.5 SQLite 边界策略

- **入库**：项目 / 工单 / 预提审元数据 / 评论 / 终端会话元数据 / 配置 / 审核结论 —— 结构化、低并发、本地单用户，SQLite 完全胜任。
- **落盘**：完整 diff 文本、终端原始流、长审计日志 —— 按 `项目/工单/轮次` 分目录存文件，DB 仅存**相对路径 + 大小 + 哈希**。
- **不入库**：git log / git tree（派生视图，§3.1）。
- 收益：DB 常驻轻量（§5 目标 < 100 MB）、易备份，避免大文本拖慢查询。

### 10.6 Schema 迁移（v2 新增，v1 缺失）

SQLite 同样需要版本化迁移：引入 **Flyway 或 Liquibase**，DB 内维护 schema 版本号，禁止手工改表。否则第一次结构调整就要手工救数据。启动时校验版本，不匹配则拒绝启动并提示迁移。

## 12. 为什么不用现成方案（v2 新增章节）

立项评审必答。v1 完全缺失，导致无法判断本项目是否值得自建。**以下为 2026-08 实际检索结果，非凭记忆罗列。**

### 12.1 结论先说

**本项目的三个能力单独看都已有成熟开源实现，但"三者合一 + 结构性闸门"这个组合目前没有找到对应项目。** 同时必须承认：**赛道很拥挤**，且有两个项目已经非常接近本项目的核心设想（见 12.4 的 agent-mesh 与 gitproxy）。

### 12.2 类别一：本地 LLM 代码审核 CLI（这一层已彻底饱和，不要自建）

检索到大量成熟项目，全部支持 Ollama 本地模型 + 结构化 findings + pre-commit/pre-push hook：

| 项目 | 语言 | 特点 |
|---|---|---|
| `dshills/prism` | Go | 最完整：6 种审核模式、4 provider、SARIF 输出、**大 diff 自动分块并发**、缓存、确定性退出码 |
| `mshykov/local-review` | Go | 单静态二进制、多 LLM **并行 fan-out 后合并 findings**、`major/critical` 非零退出可作闸门 |
| `CommitBrief/commitbrief` | — | **已内置 MCP server（stdio），明确定位为"agent 提交前的自审闸门"** |
| `un/gitPreflight` | TS/Bun | **专为 AI coding agent 设计**的 staged-only 提交闸门，输出 LLM 友好 Markdown 供 agent 直接修复；支持 local-agent 模式（Codex/Claude/**OpenCode**）；有 offline/timeout 的 `UNCHECKED` 积压策略 |
| `MehulKChaudhari/gitgandalf` | Node | 纯本地 LM Studio，LOW/MEDIUM/HIGH → ALLOW/WARN/BLOCK，**prompt 带版本号** |
| `Dshuishui/airev` | — | 复用已登录的 CLI（claude/codex/gemini/copilot），零 API key |
| `faw21/critiq`、`aicrcli`、`commit-review`、`revcli`、`lfylow/codereview-mcp` | 多 | 同类，各有侧重 |

**对本项目的影响（重要）**：§13.1 里"`review_run` 调审核模型 + §7.3 结构化 schema + §7.2 分块"这部分**不应从零写**。至少应评估直接**复用/包装 `prism` 或 `local-review` 作为审核引擎**（二者都是单二进制、有确定性退出码、有 SARIF/JSON 输出），把自研聚焦在闸门与工单编排上。这能砍掉 M1 相当一部分工作量。

### 12.3 类别二：agent 编排 + worktree + 看板 + 终端（这一层也很拥挤）

本项目 §3/§11 设想的"项目-工单-看板-内嵌终端-diff 审核"UI，已有多个完成度很高的实现：

| 项目 | 栈 | 与本项目重叠处 |
|---|---|---|
| `ShreyPaharia/octomux` | TS, MIT | 一任务一 worktree、kanban、**Monitor grid 多终端**、in-app diff review、**审核 agent 起草 + 人类批准后才发布**、~130 REST + WS(xterm↔tmux) + SQLite |
| `fynnfluegge/agtx` | TUI | 一任务一 worktree + tmux、**内置 MCP server 把看板暴露给 agent**（`move_task`/`read_pane_content`/`send_to_task`）、按阶段切换不同模型（Gemini 研究 / Claude 实现 / **Codex 审核**） |
| `loicngr/kobo` | **Hono + Vue3/Quasar + SQLite(WAL) + WS** | **技术栈与本项目 §9 高度相似**；Monaco diff、per-workspace MCP server、多引擎 |
| `armueller/agent-mesh` | TS + React Router + SQLite | 见 12.4 |
| `devinrosen/conductor-ai` | Rust | worktree + 工单(GitHub/Jira) + 工作流 DSL，**DSL 里有 `gate` 步骤做人工/自动审批** |

**对本项目的影响**：§13.2 已把看板/多终端/项目管理 UI 推迟到 M2，这个决定现在有了更强的依据——**这一层不但不是差异点，还是别人的主战场**。

### 12.4 最接近的两个项目（必须逐条对比，不能忽略）

**`armueller/agent-mesh`** — 与本项目核心设想重合度最高：

- MCP proxy（stdio）→ 本地 Web app（`127.0.0.1:3847`）→ SQLite，spawn Claude CLI 到 `.agent-mesh/worktrees/{task_id}/`；
- agent 调 `commit()` → **自动 spawn 一个只读 review agent** → 返回 `CONTINUE` / `FEEDBACK`（注入反馈并 resume）/ `APPROVED`；
- `APPROVED` 后**仍需人类在 dashboard 里 squash-merge 才进 main**；
- 其 README 明确写：**单用户 localhost，无 auth、无 CORS、无 rate limit，且"当前路线图没有加 auth 的计划"**。

**与本项目的关键差异（即本项目仍有的价值）**：

| 维度 | agent-mesh | 本项目 v2 |
|---|---|---|
| 闸门性质 | **约定式**——agent 调 `commit()` 走流程；未见服务端 `pre-receive` 强制 | **结构性**——bare + `pre-receive`，`--no-verify` 跳不过（§6.1） |
| TOCTOU | 未见 tree 固化机制 | 审核锚定不可变 `tree_hash`，commit 前复核（§6.3） |
| 权限域 | MCP 工具按 client type 分组，但同一 localhost 无 auth | agent 域 / 人域**两套凭据 + Origin 校验**（§6.2） |
| 审核员独立性 | review agent 与执行 agent 同为 Claude CLI | 审核模型与执行模型**配置解耦 + 同模型告警**（§7.1） |
| 成本度量 | 无 | H1 埋点与止损判据（§1.3、§15） |

**`afq984/gitproxy`** — 与本项目 §6.1 闸门思路**高度一致，且做得更狠**：

- 持凭据的 Git-over-HTTP 反向代理，agent 永远看不到 token；
- 读操作放行，**拦截 `POST .../git-receive-pack`**，解析 ref update，人工批准后才转发；
- **单次使用、内存态、仅在上游确认成功后消费的 approval token**，超时自动拒绝，绑定 `(ref, new_oid)`；
- 明确声明"**不替代代码审核**"，只回答"这个 commit 能否发布到这个分支"。

**这几乎就是本项目 §6.1 + §6.4 的独立实现。** 本项目的令牌语义（一次性、用后即焚、绑 `tree_hash`）应直接对齐它，而不是自己重新设计。

**`Jose-Ribeir/claude-code-review-gate`** 也值得看：它把 gate 做成 `pre-push`（而非 `pre-commit`），理由与本文档 §6.1 完全一致；并且**fail-closed**（超时/崩溃/无法解析 → 阻断），这一条本项目 §6.4 没写，应当补上。

**`CodeDeficient/opencode-review-enforcement`** 提供了第三条路：**用 `git notes` 挂审核结论 + `pre-push` hook 校验 notes**。比令牌方案更轻，值得在 S1 spike 时一并评估。

### 12.5 检索带来的三条结论

1. **审核引擎不要自研**——直接评估复用 `prism` / `local-review`（M1 可省一大块）。
2. **看板/终端/编排不要自研**——已推迟到 M2 是对的；若最终仍需要，优先考虑在 `octomux` / `agtx` 上做插件而非重写。
3. **本项目真正的、目前无人完整覆盖的差异点只剩三条**：`pre-receive` 结构性闸门 + `tree_hash` 防 TOCTOU + 审核员独立性与成本度量。**这三条撑不起一个"大项目立项"，但撑得起一个"闸门层"组件。**

### 12.6 修订后的自建理由（必须同时成立）

1. 纯本地 / 可离线，代码不出机器；
2. **结构性闸门**：未审核代码在**接收端**被拒（§6.1），且锚定 `tree_hash` 防 TOCTOU（§6.3）——这是与 agent-mesh 等约定式流程的本质区别；
3. **审核员独立性可强制**：审核模型与执行模型配置解耦（§7.1）；
4. 执行 / 审核成本可度量且有止损判据（§1.3、§15）。

> 注意：v1 曾把"工单 + 终端调度 + 审核三者一体"列为自建理由，**v2 检索后删除该条**——octomux / agtx / kobo / agent-mesh 已充分覆盖，不构成差异点。

**止损条件（任一触发即缩减范围）**：

- 上述 1–4 有任意一条不再成立；
- 或 H1（§1.3）被证伪；
- 或 §12.5 结论 1/2 落地后，发现剩余自研量已不足以支撑独立项目。

**缩减后的目标形态**：不是"整套系统"，而是**一个闸门层组件**——`pre-receive` + `tree_hash` + 令牌 + 审核员独立性，审核引擎复用 `prism`/`local-review`，编排层挂在 `octomux`/`agtx` 上。这条写进立项文档，作为主动止损路径。

## 14. 测试策略（v2 新增章节）

v1 自称"可靠性优先"却无测试计划。对一个以"闸门"为核心价值的系统，闸门测试就是产品测试。

### 14.1 git fixture 套件

- 用 JGit 以代码方式构造临时 repo：bare 权威库 + worktree，预置各类改动（新增 / 删除 / 重命名 / mode 变更 / untracked / 二进制 / submodule / `.gitignore` 漂移）。
- 每个测试独立临时目录，测试后清理；**不依赖开发者本机 git 配置**（显式设置 `user.name` / `user.email` / `core.autocrlf`，Windows 上尤其重要）。

### 14.2 闸门绕过测试集（最高优先级，逐条对应 §6.1 攻击面）

**每一种绕过方式都写成一个测试，断言权威库 HEAD 未变**：

| # | 攻击 | 期望 |
|---|---|---|
| B1 | 在 worktree 里 `git commit --no-verify` 后尝试 push | `pre-receive` 拒绝 |
| B2 | `git -c core.hooksPath=/dev/null commit` 后 push | 拒绝 |
| B3 | 删除本地 hook 后 commit 并 push | 拒绝 |
| B4 | 纯 plumbing（`hash-object` / `write-tree` / `commit-tree` / `update-ref`）后 push | 拒绝 |
| B5 | 伪造 / 重放已用过的审核令牌 | 拒绝（令牌用后即焚，§6.4） |
| B6 | 携带合法令牌但 push 的 tree ≠ 被审核的 `tree_hash` | 拒绝 |

### 14.3 TOCTOU 与幂等回归

- 审核通过后修改工作区 → `commit_execute` 必须拒绝并退回预提审（A4）。
- 同一 `(ticket, round, tree_hash)` 重复调用 `commit_execute` → 只产生一个 commit（§6.4）。

### 14.4 权限域测试

- 用 agent 域 token 遍历**全部**人域 tool，逐一断言 403（A5）。新增 tool 时该测试必须同步扩展（用清单驱动，避免漏测）。

### 14.5 故障注入

- 在 `write-tree` 后 / `commit-tree` 后 / `push` 中途 / `push` 成功但落库前，各注入一次进程终止，验证 reconcile 收敛（A7）。

### 14.6 审核员测试（不打真实 LLM）

- provider 层可替换为 stub，返回固定 JSON，验证 §7.3 schema 解析、判定规则（blocker → reject）、回喂链路。
- 真实模型调用仅在少量手工冒烟测试中进行，避免测试成本与不确定性。

## 15. 成本度量与埋点（v2 新增章节，服务 H1）

H1（§1.3）是本项目的立项理由，必须可验证，否则无法判断成败。

### 15.1 埋点字段（随工单落库）

- `exec_token_cost`：prompt / completion 分开，累计整个工单所有轮次。
- `review_token_cost`：同上，按 `review_round` 明细 + 汇总。
- `review_round`：审核轮次。
- `verdict_history`：每轮结论与 blocker 数量。
- `diff_size`：行数 / 字节数（用于分析成本与 diff 规模的关系）。
- `prompt_version`、`executor_model`、`reviewer_model`。

### 15.2 判定指标

- **审核成本占比** = `review_token_cost / (exec_token_cost + review_token_cost)`，取中位数。
- **一次通过率** = `review_round == 1 且 verdict == pass` 的工单占比。

### 15.3 判定时点与结论

- 样本量 ≥ 20 个真实工单（A8）后做首次判定。
- 占比 < 20% 且一次通过率 > 60% → **H1 成立**，按 §13.3 推进 M2。
- 占比 20%–40% → **部分成立**，优先做 §7.2 增量审核与分块优化，再复测。
- 占比 > 40% 或一次通过率 < 40% → **H1 证伪**，按 §12 止损条件缩减范围。

> 这一节的意义是：让项目有一个**可以被数据否决**的机制，而不是做完才发现不划算。

| # | Spike | 验证内容 | 失败后果 |
|---|---|---|---|
| **S1** | **agent CLI 能否注入自定义 MCP server 配置** | opencode / claude code 是否支持指向本系统的 MCP endpoint（HTTP/SSE 或经 stdio bridge）；能否在启动时以参数 / 配置文件注入；能否携带 agent 域 token。参考 `agtx` 用 `claude mcp add-json --scope local` 注册的做法（§12.3） | B 模式（§10.3）的"MCP 回写"不成立 → 降级为 stdout 协议解析或人工触发预提审。**闸门本身不受影响**（§6.1 在接收端），但自动化程度大幅下降 |
| **S2** | **Java PTY 在 Windows + macOS 的交互式验证** | spawn agent CLI 后：交互式输入、`Ctrl-C`、resize、ANSI 颜色、**进程树整体 kill** | 内嵌交互式终端不可行 → 按 §9.4 降级为非交互式 spawn + 只读日志 |
| **S3**（v2 新增，来自 §12 检索） | **审核引擎能否复用现成项目** | 跑通 `dshills/prism` 与 `mshykov/local-review`：JSON/SARIF 输出是否稳定、退出码是否确定、能否指定 Ollama、大 diff 分块行为、Windows 上能否运行 | 若可复用 → §13.1 砍掉自研审核引擎，M1 大幅缩小；若不可用 → 才自研 §7.2/§7.3 |
| **S4**（v2 新增，来自 §12.4） | **闸门实现路线对比** | 三种方案实测：① bare + `pre-receive` + 令牌；② `git notes` + `pre-push`（参考 `opencode-review-enforcement`）；③ HTTP 反向代理拦 `git-receive-pack`（参考 `gitproxy`）。在 Windows 上各自的可行性与绕过面 | 选错路线会导致 §6.1 返工。**这是 M1 的技术核心，必须先定** |

**四个 spike 都有结论后，再进入技术方案与工作分解。** v1 的错误正是跳过 S1（用错误的"hook 是物理闸门"推理把它降级为非阻断）。S3/S4 是 v2 检索现成方案后新增的——**先确认哪些不用自己写，再决定写什么**。

> **后续进展补注（2026-08-14）**：四个 spike 全部有结论。S1/S3/S4 通过，S2 因定位收窄（不再需要内嵌终端）而删除。详见文首「后续进展」B 节与 `../归档/done/spike-结论.md`。**此节之后项目已进入并完成技术方案与实现**（P0–P4，见 `../归档/done/执行文档.md` 与 `../归档/done/acceptance-report.md`）。

## 17. 风险与开放问题

| 风险 | 现状 | 缓解 |
|---|---|---|
| **diff 爆炸** | 大 diff 审核成本高，直接威胁 H1 | §5 体积阈值拒绝 + §7.2 分块与增量审核 |
| **误杀 vs 漏杀** | 审核太严反复打回，太松失去意义 | 严格度可调（§7.3 判定规则）+ 人工兜底 + §15 一次通过率监控 |
| **agent 与系统同权限，无绝对隔离** | 已在 §6.1 明示接受 | 审计留痕可事后发现（§6.5）；容器化列 M2（§13.3） |
| **S1 失败**（CLI 不支持 MCP 注入） | 未验证 | §16 降级路径；闸门不受影响 |
| **S2 失败**（PTY 不可用） | 未验证 | §9.4 降级为非交互式 spawn |
| **审核质量不可回归** | prompt 改动导致历史不可比 | §7.3 prompt 版本号 + M2 建质量回归集（§13.3） |
| **分支 / worktree 爆炸** | 长期运行累积 | §8.4 生命周期清理 + reconcile 扫描 |
| **JGit 与真实 git 行为差异** | 边缘场景（CRLF、mode、submodule） | §14.1 fixture 覆盖；差异场景改用 `ProcessBuilder` 调真实 git |
| **LLM provider 不稳定 / schema 不遵守** | JSON 输出可能不合规 | structured output 强约束 + 解析失败重试 1 次 + 转人工 |
| **单点 SQLite 损坏** | 本地文件风险 | DB 轻量（§10.5）+ 定期备份 + git 为最终真相（§6.4 可重建状态） |
| **赛道拥挤，差异点收窄（v2 新增，最高级别）** | §12 检索显示审核 CLI 与 agent 编排两层均已饱和，agent-mesh 与 gitproxy 已非常接近核心设想 | 差异点收敛为三条（§12.6）；S3/S4 先确认可复用范围（§16）；触发止损则退为"闸门层组件" |
| **重复造轮子的沉没成本** | 若不先做 S3/S4 就自研审核引擎与闸门 | **S3/S4 为进规划的硬前置**，未出结论不得开工 |
